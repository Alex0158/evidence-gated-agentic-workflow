# 工作規則與標準

本檔合併三類規範：協作與變更、工程品質、測試與 evidence。它們定義 must-hold、適用範圍與判定方式；具體操作步驟由[Runbooks](../README.md)路由，精確命令與工具設定由[項目工程入口](../項目工程入口.md)指向的 native binding 唯一承接。本檔不存產品規則、secrets 或單次執行結果。

## 一、協作、決策與變更

1. **分清角色責任**：canonical source／owner 定義內容；decision authority 有權確認產品方向、契約或風險；maintainer 更新文件／實作；participants 參與分析與 review。單人可兼任多種角色，但維護身份不自動帶來產品決策權。
2. **依現有授權行動**：已確認需求內的小幅深化與可逆工作可直接推進。改變全局方向、scope、權限／資料政策、相容性、重大風險接受或外部承諾時，先提出明確選項給相應 owner；Runbook、AI 推論、branch、PR、測試通過或文件 timestamp 都不構成批准。跨層或長期變更實作前，依風險判斷是否需要 tracking issue、spec 或 decision note；不為低風險小改強造記錄，也不因沒建文件而推定高影響決策已完成。
3. **確認有範圍**：已確認結果引用唯一原始確認事件，並說明它涵蓋的 scope／revision。沒有可回查的確認依據時標 pending／unknown；不可在各規格自由複製一個 Approved 值。
4. **處理來源衝突**：先核對問題、scope、適用 baseline、owner、確認狀態及直接 evidence，再分類為 defect、doc drift、新需求、環境／fixture gate、歷史差異或待決。產品意圖、native source、assertion、runtime observation 分別回答不同問題；不得以較新文件或目前 code 單獨裁決所有面向。
5. **管理採納範圍**：全部採納只更新被確認範圍；partial 明列採納與待決部分；reject/defer 記處置和依據，不改 current contract。Proposal 仍是 proposal，除非有權事件清楚改變其身份。
6. **最小改動與回寫**：先更新 primary owner，核對會受影響的正向 consumers、tests 及必要派生視圖。只處理本次實質變動內容；不把調查筆記、單次 PASS 或一個 task 狀態提升為永久規則。
7. **例外與停止**：標準例外須有 scope、理由、決定者和期限／恢復條件（若適用）。如果缺少授權、資料 ownership、相容性決策或必要前提，停止依賴它的動作，保留安全且獨立的已授權工作。

### 外部操作、授權時點與未知結果

本分支只在外部 mutation 適用。Dispatch 前沿原 Task／交付紀錄／平台紀錄固定當時有效的批准來源、target、允許動作、適用條件及 operation identity；使用可回查的固定引用或快照，不能只連到日後可變而無歷史的批准頁面。Dispatch 後連回 service receipt，不另建 grant 或 operation 台帳；文件記錄本身不是 IAM 或 runtime enforcement。

Timeout／disconnect 不單獨證明失敗。先保留外部操作的 outcome unknown，依 authoritative readback、stable business identity 與原 receipt 對帳；batch 逐項保留 success／failure／unknown。若服務有 eventual consistency，早期查無仍可能是 unknown，不能因此盲目重送或聲明完成。這是操作狀態，不取代下文的測試結果定義。

只有服務契約已核實支援 idempotency 時，才依已知 scope、TTL、request-match 及 replay 條件使用原 key；不換新 key 重送，也不把沿用 key 宣稱為 exactly-once 或撤銷操作。沒有此能力時，仍先用 stable identity／receipt 與權威來源對帳；無法判定時停止相依重試與完成聲明，保留安全且獨立的已授權工作及下一個查證 owner。

One-shot 授權在 dispatch 時視為已消耗，未知結果不會使它復活。Target、tool、format、權限面、scope 或風險實質改變時，重核授權是否仍適用；撤銷／到期後的在途操作、補償、rollback 及有副作用驗證，各依仍有效的明確授權處理，不由原 action 或技術需要自動續權。既有仍適用的授權不重問。

### 資料來源與表示權威

當資料來源或欄位可改性有歧義時，追 request→authoritative source／owner→server-side validate、normalize、ignore、derive 或 overwrite→persistence→consumer；未查清的環節保留為 ambiguity，不以 request value 推定權威。產品／業務 owner 決定資料意義、可改性與預期結果；技術／native owner 決定 schema、API、程式與儲存表示，兩種責任不能互相代替。

### 破壞性操作

刪除、覆寫取代、reset／clean／restore、破壞性資料準備／migration 或外部狀態寫入，同時受執行環境提供的 global AGENTS.md instructions 與[本項目 AGENTS.md](../../../AGENTS.md) 約束，並須通過兩道 gate：**必要性**—先解析 exact target list，證明操作與本任務直接相關並考慮非破壞替代；**影響與可恢復性**—核 boundary、ownership、tracked／untracked／ignored／modified 狀態、blast radius 和精確 recovery source。若 target 位於 workspace/repo 外、untracked／ignored／modified、非本任務建立、屬 backup／data／media／archive、可能供其他工作使用，或無法證明可恢復，先停止並取得對 exact targets 的明確確認。技術需要不等於授權；既有明確授權不重問。執行前立即重新解析並逐一核對 exact target list；global 與 project 規則皆適用時兩者都須滿足。此處是本 candidate 唯一的破壞性操作規則定義，Runbook 只引用並套用到相關分支。

## 二、工程品質

1. 按項目 native code/config 和現有分層修改；避免把產品邏輯放入入口文件、生成物、reference code 或不屬於本次 scope 的 shared platform。
2. 先理解改動的 source boundary 和 consumers，再做最小而可 review 的變更。保留相容性契約、錯誤語義、資料 ownership 與權限邊界；偏差回報 canonical owner，不以重構順手擴大 scope。
3. Generated、vendor、schema、migration、API、type definition、design token 和 scripts 各須由項目明示的 owner 綁定；本標準不假定任何工具／語言／目錄已存在。未交接前，已確認 MD contract 可承接設計定義。
4. 工具值、格式規則、build／lint／type-check 設定回 native config 或[項目工程入口](../項目工程入口.md)指向的唯一 binding，不在本標準重抄。只執行項目實際宣告且適用的檢查；缺 runner 時說明 no runner，不能編造通用命令。
5. 不把 secrets、憑據、個人絕對路徑、真實敏感資料寫進通用底座、source、log 或測試 fixture。使用隔離且可重建的資料；涉及 destructive data、migration 或外部系統寫入時，遵循[破壞性操作](#破壞性操作)規則。
6. Review 要能辨認預期、改動、受影響 consumers、驗證層級及剩餘風險。檔案長度、helper 數量或固定目錄完整度不是通用品質門檻。

### 工具能力與身份

需要外部工具／Connector 時，針對本次操作區分 configured／installed、在當前任務 exposed、authenticated、正確帳號／workspace、exact target readable、所需 write capability 及實際 mutation authority。設定或工具名稱存在不足以證明後續各層；能讀不等於能寫，能寫也不等於獲准寫。先完成必要的唯讀查證，再按原授權與適用 gate 操作；外部寫入結果依[未知結果規則](#外部操作授權時點與未知結果)處理。

實際工具值與帳號取得方式回工程 binding／authorized secure retrieval，一次查證結果回原紀錄。不新增能力清單或模板，不要求與外部工具無關的本地檢查填這個階梯；缺少哪個必要層，只限制依賴它的 claim／操作。

## 三、驗證與 evidence

### Claim 與 evidence path

先定要證明的 claim、可觀察邊界與 evidence path，再選能支持它的最小驗證。一般使用者流程、direct API/security contract、integration、runtime、deployment 與 acceptance 是不同 claim；source inspection、靜態文件檢查、build、test execution、runtime、部署及 user-visible behavior 也分開記錄。沒有 UI 入口不代表 API 安全；API direct test PASS 只支持該 API/security claim，不證明完整使用者流程。需要證明 API security 時，檢查後端 route／handler 與 server-side guard，並用符合風險的 direct request evidence；需要證明 user workflow 時，驗證實際入口到可觀察結果的鏈路。低層 evidence 不外推到省略的邊界。

影像是否需要產生或保存，依本次 claim 與驗收目的決定。涉及影像證據選擇時，在本次 run 的既有方法／限制欄位或 primary record 記錄選擇、理由及相應限制；引用既有影像時，核對其適用版本與範圍。未產生影像不代表未操作 UI；UI 操作與人工視覺審閱各依實際方法和觀察判定，不能把未產生影像的 run 記成已有本輪影像。不得以省略驗收必需的證據換取通過。不要求與影像無關的 run 另填截圖政策。

### 結果與狀態

驗證方法可以是 native runner、人工／工具操作或 source／文件核查，按本次 claim 選擇並記錄實際方法、前提與觀察。只有該項檢查需要 native runner 時，缺 runner 才令該項 NOT_RUN；其他已實際完成且有 evidence 的核查可各自判定結果，不能代替缺失的產品測試或更高層 claim。人工／工具方法不授予新操作權，必要命令仍核對工程入口與實際來源，不得臆造。

- **PASS**：指定 assertion／claim 實際執行並符合預期，且來源、scope 和環境可追溯。
- **FAIL**：實際執行觀察到相對該 assertion 的不符合；接著分類，不代表根因已知。
- **SKIP**：本次有意不執行，須記原因、依據及省略範圍；不必先執行才能記 SKIP，也不因省略而取消原有驗收要求。
- **NOT_RUN**：該項檢查尚未執行，或其必要 runner／環境／依賴未具備；明示缺少的前提。它不是 PASS，也不描述其他已完成檢查的結果。
- **BLOCKED**：工作／claim 被指定依賴阻塞的狀態，不是 test 結果。

結果／阻塞狀態與 cause／owner 是兩條軸：結果描述本次 claim／步驟是否執行及觀察，cause 描述為何失敗或受阻、由誰處理。BLOCKED 不代表 PASS、non-defect 或已知根因；若不可用的 gate 本身是本次產品／交付承諾，另定該 gate 的 claim 並查它是否履行，不能讓 blocker 代替 gate evidence。覆蓋資產存在、ID 命中、文件檢查通過、expected-fail、stub pass 或 build 成功，都不能冒充適用測試結果。Health up 不代表業務鏈路可用；部署完成不代表 user acceptance。

### Evidence 綁定與回寫

每個可作結論的 run 記錄適用的 source revision／artifact、scope、environment、實際 command 或方法、前提、expected／observed、結果、失敗分類與未驗範圍。需要 native runner 時，其入口／可重用命令從[項目工程入口](../項目工程入口.md)所指唯一 binding 取得；人工／工具核查保留實際操作與來源，不把一次操作紀錄變成另一份工程配置。舊 run 保持其原 baseline，不改寫成新版 PASS；重用舊 evidence 時說明為何仍適用。

沿用 run 的來源欄位連到已固定、可取得且可核對實體內容的 revision／artifact、來源快照、基準加差異 reference 或等價來源引用。多次 run 使用同一份來源時可共用引用，毋須逐次複製；各 run 的方法、環境、結果與適用範圍仍分別保存。只涵蓋影響本次 claim 的輸入，不複製無關 workspace 或 secrets；來源或相關輸入有變時，須辨識本次實際內容。單獨的 hash 或可變路徑不能代替可取得的來源；若透過 manifest／索引引用來源，亦須固定該 manifest／索引本身的內容身份。不強制採用特定快照工具、儲存方式或 manifest 格式。

若實際使用的 source／config 或其他相關輸入含未提交、未追蹤改動，Git commit 本身不足以代表本次內容，依上段補足來源引用，必要時附 hash。VR／交付紀錄共用這份來源引用，不另造台帳；不得因不同內容沿用同一 commit 就沿用 PASS。無法辨識或取得實際內容時明示 provenance 缺口，限制相依結論。這不要求先 commit 或清空 working tree。

逐項 check 的實際結果只在選定 run record 的正文記錄；header、summary 或 coverage view 引用／派生，不另手填同一結果。混合 PASS／FAIL／SKIP／NOT_RUN 時保留各項及其對 claim 的限制，不用摘要掩蓋未覆蓋條款。Source 搜尋的「未找到」須附實際範圍、方法及限制，只支持該範圍的觀察。

驗收門檻由產品／契約 owner 定義，測試資產定義 assertion，本次 record 保存觀察。Verify-only 不授權修復、改測試以迎合結果或調低 acceptance；需要新 scope 時回到相應 owner。每次選最小適用 layer，不要求每個小改動跑全量套件或新建完整 Golden 資產。

## 例外與更新

本標準變動只更新確實改變的治理、工程或 evidence 條件。一次結果回到 dated record；native tool setting 回 native source；產品門檻回產品 owner。使用者已授權的範圍內可以深化細節，但不可自行改變本標準沒有授權的產品方向或風險接受。
