# Runbook：驗證功能

## Trigger 與 verify-only 邊界

當要證明一個已定義的產品 acceptance 或工程 claim 時使用，可單獨 verify-only，也可接在開發／修復之後。Verify-only 只允許計畫與執行本次驗證、記錄結果和提出分類；它不自動授權修復、修改產品門檻、改寫 assertion 使結果通過或部署。

## 讀者與前提

Acceptance owner、test／驗證 maintainer、執行者和 reviewer 依 claim 讀取：正式 AC／契約、[工作標準](../規則與標準/工作規則與標準.md)、[項目工程入口](../項目工程入口.md)、必要環境／fixture 前提，以及有關聯的測試計劃／coverage／既有 verification record。先核對適用的 source revision、branch、artifact、environment、資料 ownership，以及所選方法需要的工具／runner 是否存在；不要求人工或 source 核查具備無關的產品 runner。

## 按需檢查

- 要支持的精確 claim 是甚麼？它的 AC owner、條款與適用 baseline 在哪裡？
- Assertion 真正檢查了哪些關鍵條件、拒絕分支、副作用或資料邊界？
- 本次驗證省略甚麼；那個缺口是否正是風險所在？
- source、artifact、environment、fixture 和 runner 的身份是否一致且可重建？
- 本次是 verify-only，還是另有既存明確修復授權？

## 操作程序與判斷分支

1. **界定 claim 並還原驗收鏈路**：先依[工作標準的 Claim 與 evidence path](../規則與標準/工作規則與標準.md#claim-與-evidence-path)定要證明的行為和 evidence path，再由 actor／入口、前置狀態、輸入、決策、read／write、副作用追到可觀察結果。API/security claim 即使找不到 UI caller，也直接檢查 route／handler、server-side guard 和適用的 direct request；這種結果只支持 API/security claim。若 claim 是完整 user workflow，需驗證真實使用者入口到結果的鏈路。AC 缺失或不清楚時，不自行補成已批准門檻；記錄缺口，沿[規格驅動開發](規格驅動開發.md)交相應 owner 釐清／確認後返回本步。Verify-only 可整理有界 proposal，不因此取得修改 current 或實作權；規格確認變更後重核 claim、assertion 及舊 evidence 的適用性。
2. **檢查既有 coverage 與 evidence**：分開資產存在、AC 對應、assertion 有效、run 已執行、結果通過。若引用舊 evidence，核對版本、scope、environment 與本次變更是否仍適用；舊結果仍是舊 run。調整 runner、證據保存或報告方式並聲稱保留覆蓋時，對照原 assertions 的判定條件、預期結果／副作用、對應輸入、實際執行分支及結果；相同 check 數量或 IDs 不代表相同覆蓋，不能因工具優化而默默縮減驗收。
3. **選最小適用層與方法**：按 claim 選 static inspection、unit、integration、E2E 或 runtime，明確使用 native runner 還是人工／工具核查。必要時將 happy path、拒絕、失敗、重試、副作用分配給能真實判斷它們的 layer；不為 ID 命中或檔案存在加 PASS。API 測試 PASS 不升格為完整 user-flow PASS。涉及影像選擇時套用[Claim 與 evidence path](../規則與標準/工作規則與標準.md#claim-與-evidence-path)，不另定截圖門檻。若本次要比較優化成本，先固定比較範圍、輸入及量度口徑；無法控制的差異列為限制，不把這項比較加到無關驗證。
4. **準備安全前提**：按環境／fixture owner 和既有 native 步驟使用隔離 fixture、測試帳戶及已授權 dependency。前提缺失時不使用 production data 或擅自 reset；若所需步驟會刪除、reset、overwrite 或改變外部狀態，遵循[破壞性操作](../規則與標準/工作規則與標準.md#破壞性操作)和[本項目 AGENTS.md](../../../AGENTS.md)，通過兩道 gate 並在執行前重核 exact target list。可獨立完成的 source review 繼續。
5. **執行所選方法**：依[工作標準的結果規則](../規則與標準/工作規則與標準.md#結果與狀態)選適用分支，保留實際操作與結果。
   - Native runner：命令從[項目工程入口](../項目工程入口.md)所指唯一 binding 讀取，核對 command、scope、inputs 與預期；必要 runner 為 null／不存在時，該項 NOT_RUN，說明缺口。
   - 人工／工具或 source 核查：記實際方法、輸入、source／target、時間、expected／observed 及證據位置；不因沒有產品 runner 抹去已完成的核查。未執行仍為 NOT_RUN，結果只支持所選 claim，不冒充自動 tests 或完整 runtime。主張「未找到」時記實際搜尋範圍、方法及限制。
6. **分類並分支**：
   - PASS：只支持指定 claim、版本、環境和已執行分支。
   - FAIL：保存現象並分類 product、test/verifier、fixture、environment、tooling 或 flaky；有原有修復授權才去[修復缺陷](修復缺陷.md)，否則只 handoff。
   - SKIP：記明有意省略的 assertion／原因及影響。
   - NOT_RUN：該項尚未執行，或所選方法需要的 runner／環境／依賴未具備；說明缺少前提及仍可支持的其他 claim。
   - BLOCKED：記錄造成阻塞的 dependency、cause／owner，只阻塞依賴它的 claim；按工作標準的[結果與狀態](../規則與標準/工作規則與標準.md#結果與狀態)處理。若被阻塞的 gate 本身是本次產品／交付承諾，另走適用證據路徑查 gate，不能由 blocker 推出它已通過或屬非缺陷。
   - Partial：分列已通過、失敗、略過、未執行與未知條款，不用整體 PASS 掩蓋。
7. **記錄結果**：更新既有 verification record／task／primary tracker，帶上 source／artifact、revision、environment、command、日期、scope、expected／observed、結果、cause／owner、evidence location 和限制。若評估優化成本，在同一結果來源列出新增或轉移的操作、儲存及維護成本；涉及儲存或打包比較時，區分日常取用、完整傳輸與全部展開後存量，不能以局部減少推定整體節省。

## 輸出與驗證

驗證發現需後續處理的重要問題，依[任務登記與分流](任務登記與分流.md)先捕捉或更新既有項，引用原 run 的實際結果；分流與登記不擴大 verify-only 的修復權，Task 狀態也不改寫原 FAIL／NOT_RUN。

確認報告中的 PASS 對應實際執行的 assertion；AC-to-test 關係可從既有 asset／mapping 回查；資料與 environment 支持本次條件；結果不外推至未跑分支、另一版本、另一環境、deploy 或 acceptance。靜態命中只表示可能的關係，需核 assertion 真正判定條件。

## Failure、stop 與 recovery

若資料／外部操作未獲授權、scope 不明、fixture 不安全或適用 gate 未滿足，執行前停止相依操作。已授權且符合安全前提的 fixture 操作可繼續；適用的破壞性／外部寫入分支仍按[破壞性操作](../規則與標準/工作規則與標準.md#破壞性操作)完整核 gate，並在執行前重核 exact targets，不因驗證需要而擴權。外部 gate 不可用時保留相依檢查的 NOT_RUN／blocked，不以 stub 或 health check 冒充真鏈路。

若 execution 與 source baseline 不一致、結果不穩定或 verifier 有錯，保留原 run 並建立新 run 作更正；不把舊 FAIL 改成新 PASS。Verify-only 發現需要修改規格／程式／測試時停在分類與 handoff，除非另一份明確授權已覆蓋該變更。

## 最小回寫與 Exit

驗收門檻回需求 owner，assertion 回測試資產 owner，本次實際結果回 verification record／tracker，evidence 方法變更才回標準／Runbook。只更新因 scope 或 owner 改變而失效的 coverage／引用。Exit 報告 claim、source／environment、已執行與未執行的分支、結果／cause 與未驗證範圍；verify-only 可完成，而產品缺陷仍 pending。
