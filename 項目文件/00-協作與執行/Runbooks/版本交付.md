# Runbook：版本交付

## Trigger 與交付層

需要建立或交接版本產物、package、部署、migration／configuration change、操作手冊或 release 時使用。先說清本次交付層：本地 build／package、交給另一 owner、部署至指定 target，或用戶 acceptance。這些是不同階段；不能由前一層推定後一層已完成。

## 讀者與前提

Release／artifact owner、執行者、target environment owner、驗證 owner、handoff 接收者和需要時的產品決策者讀取[項目文件來源目錄](../../README.md)、[項目工程入口](../項目工程入口.md)所指唯一 binding、協作／工程／evidence 標準、環境前提、適用 current contract／decision、必要 migration／config／runtime design 及既有 tracker。先確認明確授權、版本 scope、source commit、artifact owner、target、資料 ownership、相容性、secret retrieval 與 recovery plan。

## 按需檢查

- 本次承諾的是哪一個交付階段，哪個 owner 接收？哪一層不在 scope？
- Artifact 是否從指定 source／revision 產生，如何辨認其身份與完整性？
- Target runtime 使用哪份有效 config；何時生效？舊 cache／host setting／dependency 是否會使結果失效？
- Migration、資料變更、權限與相容性風險由誰決定，如何觀察及補救？
- 哪個 runner／gate 是此 claim 必需？缺少時哪個階段標 NOT_RUN／blocked？

## 操作程序與分支

1. **固定版本與範圍**：記錄 release intent、包含的功能／修正、source branch／commit、baseline、non-goals、artifact target 與接受者。未獲授權的 scope 不放進 package。
2. **選適用階段**：
   - 只 build／package：仍需核 source→artifact identity 和 artifact 檢查；不寫 deployed。
   - handoff：核接收者、版本、限制、操作前提與待完成項；不寫 user accepted。
   - deploy／migration／production change：必須有明確授權、target、變更計畫、相容性與 recovery owner。任何一項缺失，停止該階段；前面安全可完成的 build／analysis 可獨立記錄。
3. **建立來源鏈**：需要 build/package 時，使用[項目工程入口](../項目工程入口.md)中實際存在的 native runner，記錄 command、source revision、輸出 artifact ID／hash 或項目既有辨識值。只交接既有產物時核其來源及 identity，不虛構一次新 build；必要 runner 缺失的步驟記 NOT_RUN。不可手抄另一套命令值，也不可用檔名推定內容來源。
4. **核設定與資料前提**：依 runtime owner 確認設定 source、生效時機、版本相容性、migration／seed／external dependency。資料來源、可改性或 migration 語義有歧義時，依工作標準[資料來源與表示權威](../規則與標準/工作規則與標準.md#資料來源與表示權威)追清來源與處理鏈；產品／業務 owner 裁決資料語義，技術／native owner 定義 migration／schema 表示。需要形成設計時可用[技術設計與契約範本](../../../文件模板/技術設計與契約範本.md)。不要把 secret 寫入 release record；只引用 authorized secure retrieval path。破壞性資料步驟依[破壞性操作](../規則與標準/工作規則與標準.md#破壞性操作)與[本項目 AGENTS.md](../../../AGENTS.md)完成兩道 gate，執行前重解並核 exact target list；沒有授權或恢復來源時停止該階段。
5. **交接／部署前驗證**：按[工作標準](../規則與標準/工作規則與標準.md)和[驗證功能](驗證功能.md)核產物身份、完整性、相容性及目標前提，選本階段適用的 artifact／build／integration evidence。每個結果綁其真正 artifact、target、方法、時間及 scope；目標仍運行舊版本時的觀察只是該版本或準備證據，不支持新版本已生效。只 build/package 的工作可帶本階段 evidence 直接進第 8 步，不強造部署階段。
6. **執行 handoff／deploy 並核身份**：只依本次已授權的交接方式及項目已確認的 native 部署程序操作。Remote write／發布／部署須在既有明確授權、指定 target 與項目 gates 範圍內；程序本身不授權外部寫入，也不要求對仍適用的授權重問。記錄接收方／target 實際收到的 artifact identity、effective config 和所需資料狀態；身份不符便停止依賴此身份的成功聲明。
7. **交接／部署後驗證與分支**：核定接收／新 target 身份後，再執行本次承諾需要的檢查。Deploy 的 runtime／smoke／user-visible 結果須綁新 artifact 和實際 target；handoff-only 核接收產物、可用條件及收據，未承諾的 runtime 階段標 N/A。若交付承諾包含接手重現或證據可取用，從接收方實際取得的副本及隨附指引核對必要來源、結果和操作材料；證據可取用須驗證定位與取得，接手重現則須在承諾範圍內依指引重做操作並核對結果。明示依賴及其取得方式，不能依賴未交付、未宣告或接收者不可取得的作者工作目錄、快取或原機絕對路徑。已宣告且獲授權可取得的外部依賴／secure retrieval 可按前提使用；不強制每次更換機器、另開 Agent 或清快取。未執行或受阻的 claim 保持 NOT_RUN／blocked，不用部署前或舊版本 PASS 代替；失敗走下方 failure／recovery 分支，user acceptance 仍須其有權接受事件。
8. **記錄階段結果與交接**：在既有 release record／tracker 逐段連 source、artifact、target、migration/config、驗證、handoff、deploy、觀察、unknown、cause／owner 與接受者確認。驗證結果引用其原 run；依工作標準分開結果與阻塞原因，適用階段保留實際狀態，不強制造沒有的階段紀錄。材料分開存放時，在原交付紀錄說明各部分、取得方式及必要展開步驟，已有操作材料則引用；只交付部分時明示範圍。是否分包由項目需要決定，不是通用必備。只有本次承諾層的證據齊備才聲明該層完成；未達部分明示責任與後續，不以整體 Done 掩蓋。

**材料交付分支（適用時，沿第 3–8 步處理）：** 有手冊／操作材料或多語輸出承諾時，先校準各 deliverable family／locale 的 current MD owner／revision，再產生具名 output artifact／hash。按材料需要核對截圖基線、審閱及 publish／handoff 收據；未發生的階段保留原狀態。沿既有 artifact chain 分條目或引用已有材料紀錄，不另建平行台帳。審閱改變語義先回 MD／產品 owner，release record 不承接手冊正文；同版號不推定不同語言已校準。

## 輸出與驗證

交付 evidence 可沿 source→build→package／image→target runtime→handoff／acceptance 回查。每個階段的 claim 只在其實際 evidence 支持時成立。Package、部署、runtime behavior 和 user acceptance 分別聲明；拒絕、partial、pending 與 NOT_RUN 保持明確。

## Failure、stop 與 recovery

Artifact source 不明、hash／版本不符、設定未生效、migration 相容性未知、驗收 owner 不明、target gate 不可用或 recovery 未備妥時，停止依賴該條件的階段。保留已完成 package 及 evidence，不改標為部署成功。

外部交接／部署的 dispatch 發生 timeout、disconnect 或 outcome unknown 時，先依[外部操作、授權時點與未知結果](../規則與標準/工作規則與標準.md#外部操作授權時點與未知結果)對帳並保留原 receipt；不得把未知當成失敗重送、成功完成或自動恢復一次性授權。確定結果後才進相應的停止／恢復分支，原紀錄承接狀態，不新增台帳。

如果部署／handoff 後觀察到失敗，記錄 exact artifact／target／時間和症狀，依項目明示且授權的 recovery／rollback procedure 處理；若 recovery 會刪除、reset、clean、覆寫或改變既有資料，先按[破壞性操作](../規則與標準/工作規則與標準.md#破壞性操作)通過兩道 gate，執行前再次解析 exact target list 並核對。沒有安全程序或需要未授權資料 mutation 時，停止擴大影響並交由有權 owner。

恢復動作後，重用第 6 步的身份核對及第 7–8 步的驗證／記錄要求：確認恢復後實際 artifact、有效 config 與必要資料狀態，再按恢復 claim 查證效果。沿既有交付紀錄追加具名恢復事件並引用新 run；原失敗交付及其結果保留，恢復成功不把原版本交付改為成功。只有動作已執行、效果未驗時，明示「已執行恢復，效果 NOT_RUN／blocked」及後續責任；身份不符或查證失敗仍走原停止／handoff 分支，不自動重試部署或擴大恢復範圍。

## 最小回寫與 Exit

長期 runtime／deployment contract 回系統設計 owner，transition 成果與 scope 回產品／業務 owner，工程 binding 回[項目工程入口](../項目工程入口.md)所指唯一 owner，本次交付 receipt 回既有 release record／tracker。只回寫本次改變的 owner 與必要引用。Exit 按階段報告 source、artifact、target、實際觀察、handoff、deploy、acceptance、NOT_RUN／blocked、cause／owner 及後續責任；健康狀態或舊版本成功不能替代新 artifact 的 evidence。
