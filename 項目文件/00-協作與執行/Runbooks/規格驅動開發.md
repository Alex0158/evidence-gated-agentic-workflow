# Runbook：規格驅動開發

## Trigger 與邊界

本檔承接本框架的 SDD 子程序：以可追溯的規格／契約約束本輪設計、工作拆分、實作及驗證，並讓規格變更驅動影響分析與重新驗證。適用與 must-hold 由[工作規則與標準](../規則與標準/工作規則與標準.md#sdd-適用與規格變更)定義；本檔管理核對、補缺、確認及返回原流程的程序。

開發與修復先核本輪契約；已有 current scope、AC、確認依據及必要依賴時走沿用短路徑，不重寫 spec 或逐條重新批准。缺漏、衝突、新能力或規則變更才展開相應分支。單一 feature 不重開全局 brainstorm；新項目或重大定位／範圍重定向走[啟動項目](啟動項目.md)，原因／事實未明先走[調查與分析](調查與分析.md)。純文字／格式及無行為變更的整理不強造新規格。

產品、業務及技術內容仍由[項目文件來源目錄](../../README.md)路由到 01／02／03 或已明示的 native owner；本 Runbook、Task、DEC 及測試不另存一份可獨立修改的完整規格。SDD 可交付 draft／proposal、就緒範圍或待決事項；規格就緒、確認、實作授權、驗證通過及可交付各自判定。

## 讀者與前提

要求者、相應內容 owner、decision authority、實作者與 reviewer 依 scope 讀取：既有需求／規格、確認事件及 baseline、相關 code／native contract、業務鏈路與共用影響、既有 decision／Task／Issue，以及[項目工程入口](../項目工程入口.md)。先核本次允許分析、寫草稿、更新 current 或實作到哪一層；文件可讀、已填模板或測試通過均不新增權限。

## 按需檢查

- 本輪要達成哪個業務結果？哪些規則、成功／拒絕結果及禁止副作用必須成立？
- Current、intended、observed 的 owner、scope、revision 與確認依據是否一致？哪個缺口真正阻塞下一步？
- 這是沿用契約、補清已確認細節、改行為的 proposal、doc drift，還是尚待調查的差異？
- 誰能決定本次變更？已有確認涵蓋哪些條款，哪些仍 pending／defer／reject？
- 規格改動會影響哪些業務鏈路、共用 consumers、設計、工作、tests 及既有 evidence？

## 操作程序與判斷分支

1. **固定本輪 scope 與來源基線**：定位 primary owner、規格／AC、適用確認事件、source revision、工作目標、允許動作及 non-goals。從正式來源讀 expected，從 native source／runtime evidence 讀實作與觀察；不以目前 code、較新文件或模板單獨裁決產品意圖。只有本次範圍需要的內容才納入。
2. **選沿用或補缺路徑**：
   - 已確認契約及依賴足夠、本輪不改契約語義：直接引用本輪條款及確認，核本輪必要開工條件後返回原流程，不新增 spec 或批准狀態。依既有規格實作新功能或修復程式偏差，均可沿用此短路徑，再按適用條件進 TDD。
   - 已確認範圍內的細化：在原 owner 補足可判定的角色／資格、入口、規則、狀態／資料轉移、成功／拒絕結果、必要副作用及 AC，沿用仍適用的確認。不能把實質改變行為稱為細化。
   - 新能力、變更規則／功能／定位：先整理 proposal 及其與 current 的差異、理由、選項與業務／共用影響，進第 3 步；只更新草稿，不先把未決選項寫成 current。
   - 來源衝突、預期不明或 code 偏離：保留各 baseline 與問題，沿用仍適用的既有分類；只有事實／原因還有缺口或新 evidence 才返回[調查與分析](調查與分析.md)。已查明而只剩 decision gap 時，將具體待決範圍帶到第 3 步，不在 SDD 與調查間無新 evidence 往返。已確認契約未變而實作不符時回[修復缺陷](修復缺陷.md)，不以改 spec 或 assertion 迎合實作。
   - 只有摘要落後：以已確認 primary owner 校正文檔及必要引用；確認含義未變後走短路徑，不把純文字修訂當成新功能。
3. **確認規格變更及採納範圍**：將會改變決策的支持／反證、收益、成本、相容／遷移、風險與待決事項交有權者；重要且需追溯的取捨才用[決策範本](../../../文件模板/決策範本.md)。引用唯一確認事件及其 scope／revision／生效條件，已有有效授權及確認不重問。全部、部分採納、拒絕、延後和未確認分開保留；確認後只將其覆蓋的內容更新到原 current owner，保留舊 revision／取代關係。確認規格不自動批准實作、發布或外部動作。
4. **補足必要設計與小步計畫**：以已確認契約推導本輪必要的技術契約、依賴、相容／transition、可觀察 AC、禁止副作用及最小驗證方法；技術表示仍回原 owner。按內容選用[模組與功能規格](../../../文件模板/模組與功能規格範本.md)、[業務流程](../../../文件模板/業務流程範本.md)或[技術設計與契約](../../../文件模板/技術設計與契約範本.md)模板，不要求全套文件。將工作拆成能獨立判定結果的小步，每步能定位規格／AC、改動 owner、依賴及驗證；可用既有 Task 的幾句安排，不強建 plan／Task／AC ID 對照台帳。
5. **規格變更驅動重新驗證安排**：對照新舊規格 baseline 的已確認差異，沿[業務與共用影響分析](調查與分析.md#操作程序與判斷分支)核對受影響的設計、工作、實作／consumer、測試 assertion、fixture／環境及必要 derived view。
   - 行為、邊界、資料／權限、API／schema、依賴或副作用改變：標明哪些既有測試／證據不再支持新 claim，更新必要設計、工作與 assertion，安排受影響的重驗；不能只更新文件或沿用同一組 test IDs 就視為覆蓋。
   - 含義未變或有 evidence 支持某部分不受影響：說明比較 scope 及沿用理由，可引用仍適用的既有結果，不要求每次改 spec 全量重跑或全庫回寫。
   - 舊 run 保留原 revision、FAIL／PASS 及限制；新規格的完成判斷引用新 run，或附適用性判斷的既有 evidence，不把舊 PASS 改掛新規格。原缺陷及歷史偏差不因採納新規則而消失，處置依原 Issue／決策範圍記錄。
   - 需要執行驗證時返回原流程，沿[驗證功能](驗證功能.md)使用實際 runner／方法；尚未執行的必要檢查保持 NOT_RUN。SDD 先確定要重驗甚麼，不把重驗計畫當成通過。
6. **判斷可開工範圍並返回**：按下方[開工條件](#開工條件)交付本輪 Ready／Conditional／Not ready 的理由、可做與受阻部分及下一責任人；沿用既有紀錄，不另造就緒台帳。從[開發與變更](開發與變更.md#操作程序與分支)進入時，返回其必要設計／小步安排，再按適用條件進[測試驅動開發](測試驅動開發.md)；從[修復缺陷](修復缺陷.md)進入時，返回核對正式預期及分類，只有契約與修復 scope 仍成立才繼續修正。沒有實作授權時可完成本次規格工作，交接 proposal／就緒範圍即可。

## 開工條件

就緒判斷只針對具名的下一步，沿用[啟動項目的開工判讀](啟動項目.md#開工準備檢查)之範圍意義；局部工作不重做全局啟動。以下是對本輪內容的核對，不是固定檔案數或必填新表：

| 條件 | 本輪需要可定位的依據 |
| --- | --- |
| 契約與確認 | 行為／AC、owner、scope／baseline 及適用確認；具名隔離 PoC 引用有效實驗授權、假設及成功條件，正式產品的 proposal／unknown 仍不當 current。 |
| 業務與禁止影響 | 功能／模組／鏈路、共用 consumers 及必要資料、權限、相容性與禁止副作用邊界。 |
| 必要設計與工作 | 足以開始該小步的技術契約、改動 owner、依賴及工作安排；遠期細節可延後。 |
| 授權及安全前提 | 本次允許動作、環境／資料邊界及適用 gate；Ready 本身不授權執行。 |
| 驗證及變更影響 | 可判定結果、適用方法及所需重驗／evidence 沿用安排；必要 runner 尚缺時列建立工作的 scope，未跑保持 NOT_RUN。 |
| 阻塞未知 | 原未決來源、責任人、下一查證／決策及解除條件；只限制真正依賴它的工作。 |

必要條件成立才對所列小步給 Ready；有可獨立推進部分時給 Conditional，明列允許與阻塞邊界；必要條件仍缺給 Not ready。只有建立 runner／查證前提的工作可開始時，不把產品功能本身寫成已就緒。這些判斷不代表實作完成、tests PASS、deployment 或 acceptance。

## 回跳、例外與停止

- **TDD／整體驗證暴露預期歧義**：返回原流程並使用本程序核對或修訂契約；若已有 evidence 顯示更合理的規則、功能或定位，主動提出 proposal，由有權者決定。確認前保留 current、原失敗及未解風險，不自行改驗收讓測試變綠。
- **已確認契約不變、只是實作或測試錯誤**：依 evidence 回原流程修正正確 owner，無須重開完整 SDD。單一候選原因被推翻不代表原問題不存在。
- **已授權隔離 PoC**：可依具名實驗假設、成功條件、資料／環境邊界及停止條件推進；假設不成為正式產品 current。要採納正式功能時再核對相應確認與驗證，不因產品接受尚 pending 而撤銷獨立的實驗授權。
- **無行為變更或規格工作本身**：格式／引用整理沿用適用規則與範圍，做必要核查，不另造完整 spec；規格語義變更仍走確認及影響程序。規格草稿可交付待決內容，不要求先跑產品 tests。
- **規格後補或現況重建**：code／runtime 只證明相應實作或觀察；預期仍需由有權來源確認。保留實際先後順序，不補造事前確認或宣稱該段工作已由規格先行。
- **缺權限、owner、必要前提或重大未知**：停止依賴部分，保留安全且獨立的已授權工作；例外按[工作標準](../規則與標準/工作規則與標準.md#一協作決策與變更)記 scope、理由、決定者／授權及恢復條件。程序不授予刪除、reset、資料重置、公開或部署權；需要時仍套全部適用 gate。

## 輸出、驗證與最小回寫

結果回原 Task／Issue／決策或規格工作紀錄，包含本輪規格／AC 及確認引用、沿用或變更的差異、必要設計／小步安排、影響與重驗計畫、就緒 scope、未決及返回路徑；已有內容直接引用。穩定語義只回 primary owner，單次工作與實際結果保持各自原紀錄。

需後續調查、裁決、實作或他人接手的事項，按[任務登記與分流](任務登記與分流.md)判斷更新既有項或新增待處理，引用規格／分析主源；不為每條 AC、規格章節或未採納想法建立任務，也不把登記當需求採納或實作授權。

審閱時核對確認事件是否覆蓋 current 差異、本輪工作及驗證是否對應該規格、影響與例外是否有依據，以及新 claim 是否錯用舊 PASS。文件／靜態檢查只支持其實際範圍，規格就緒不能代替產品驗證。Exit 明列已確認、proposal／partial／defer／reject、可做與被阻塞部分、未驗及下一責任人；不由本程序自行關閉原缺陷或宣稱已交付。
