# Runbook：測試驅動開發

## Trigger 與邊界

本檔是[開發與變更](開發與變更.md)及[修復缺陷](修復缺陷.md)共用的 TDD 子程序：在已確認契約及授權內，以小步的 **Red → Green → Refactor** 推進可自動驗證的程式行為。適用範圍及例外的 must-hold 由[工作規則與標準](../規則與標準/工作規則與標準.md#tdd-適用與例外)裁決，本檔承接具體步驟、判斷與返回路徑。

新功能、行為變更及缺陷修復符合適用條件時，從原 Runbook 直接進入，不需繞經另一個主流程。原流程仍負責業務鏈路／共用影響、方案與授權、整體回歸、文件及交付；TDD 不取代它們，也不授予新產品、資料、發布或外部操作權。Verify-only 發現失敗時先分類及 handoff，已有修復授權才可進入本程序。

本輪規格／AC 已足夠時沿用；若預期不明或需要變更，先返回原流程並沿[規格驅動開發](規格驅動開發.md)核對／確認，完成影響與重驗安排後才繼續依賴該契約的小步。SDD 就緒不等於 TDD 已通過，舊規格的 Green 也不自動支持新 revision。

純文件／格式、無行為變更的整理、唯讀調查及一次性操作不強造 Red。無法安全自動化、尚未定義契約或接手本輪前目標改動已完成時，依下方[適用判斷與例外](#適用判斷與例外)處理；人工失敗證據及事後補測不稱為 test-first TDD。

## 讀者與前提

實作者、相應契約／測試 owner 及 reviewer 按需讀取：原 Task／Issue、已確認 requirement／business rule／AC、相關實作與既有 tests、影響分析、[項目工程入口](../項目工程入口.md)及適用的[驗證功能](驗證功能.md)程序。先核 source baseline、允許變更、native runner、隔離 fixture 和停止條件；不以測試需要取得 production data 或改變外部狀態。

## 按需檢查

- 本輪要改變哪一項可觀察行為或禁止副作用？預期由哪個 current owner 確認？
- 哪個最小測試層可以真實判定它？既有 assertion 能否沿用，還是缺少必要情境？
- 測試會因目標行為未成立而失敗，還是只因 runner、fixture、語法或無關依賴出錯？
- Mock／stub 是否替代了正要證明的業務規則？其他共用 consumers 需要哪些保護與回歸？
- 哪個結果足以進下一階段，哪個未知需要回原流程或調查？

## 操作程序與判斷分支

1. **選定本輪行為與方法**：固定原流程為本次調用選定的小步／AC、允許變更及完成條件，與整個 Task 的其餘工作分清；依下方適用判斷確認走 TDD 或具名替代路徑。將該小步拆成可獨立判定的必要成功、拒絕、邊界及副作用情境，不在本子程序自行接入下一個工作小步，也不預造未確認功能或完整測試清單。測試層與 runner 依[驗證功能](驗證功能.md#操作程序與判斷分支)選擇，不在本檔發明命令或固定 coverage 百分比。
2. **核 baseline 並準備測試**：檢查相關既有測試與前提，按風險跑最小基線，保留已有 FAIL／flaky／NOT_RUN。先新增、調整或沿用能判定本輪契約的 automated assertion；檢查可觀察結果及必要副作用，避免只斷言內部實作形狀、mock 被呼叫或檔案存在。只在目標契約本來就是互動／呼叫協定時，以相應互動作 assertion。
3. **Red：先觀察目標失敗**：在本輪實作變更之前執行所選測試，保留 source、測試及失敗原因的引用。修復可沿用可回查、仍符合本輪 baseline／條件的既有 automated failure，不為形式重複危險的修前操作。
   - 因目標行為尚未實作或違反契約而失敗：取得本輪 Red；實際 test 結果仍記 FAIL，進 Green，不覆寫原失敗紀錄。
   - 新接口尚不存在造成預期編譯／型別失敗，或缺少目標公開接口的 import 失敗：核實錯誤確實指向該接口缺口；補足最小可執行入口後，仍須核對目標 assertion 確實執行及判定行為，不能只以編譯成功當 Green。
   - 與目標契約無關或原因未明的語法／import 錯誤、缺 runner／fixture、timeout 或 flaky：先分類及處理前提，不直接算作目標 Red。若受控且可重複的測試證明目標截止時間、取消或逾時處理契約未成立，可記相應目標 Red；外部寫入的 timeout 仍依[未知結果規則](../規則與標準/工作規則與標準.md#外部操作授權時點與未知結果)對帳，不能推定操作失敗。無法在本次授權內處理時，保留限制並走例外或 handoff。
   - 未改實作就已通過：核對 assertion 是否有效、是否跑到正確 source，或行為本來已成立。必要時補有意義的缺漏情境；若無需行為變更，保留既有覆蓋並返回原流程，不故意破壞程式或 assertion 製造 Red。
4. **Green：實作本輪必要行為**：在授權 scope 內修改正確 owner，使目標測試通過，並跑本輪必要的相關既有測試。以已選定整體方案約束小步實作，不以局部特判取代共用規則。
   - 不刪除／弱化 assertion、調低 AC、吞錯兜底或以 mock／固定回傳繞過正要證明的行為來取得 Green；測試本身有錯時，保留 evidence，依原流程確認正式預期後修正 asset。
   - 目標或新受影響測試仍失敗：分類 production、test/verifier、fixture／environment 或未知；依 evidence 回 Red／Green，必要時回[調查與分析](調查與分析.md)。不盲目重跑到偶然通過。
   - 目標測試實際通過：只取得該 assertion 的 Green；本輪必要相關測試也通過，且沒有本輪引入的新 FAIL，才進 Refactor 或完成本次調用。原有且與本輪無關的失敗及未驗範圍照實保留；是否阻塞整體完成依原流程及項目 required checks 判斷，不要求為進此階段清零全庫既有失敗。
5. **Refactor：評估必要的行為不變整理**：以 Green 作基線，檢查本輪是否留下重複、不必要複雜度或不清楚的責任；有必要才在授權內整理，沒有必要可直接進下一步。保持外部行為及契約不變，重跑受影響的目標與相關測試。
   - 重構後出現新失敗：停下擴展，先定位並恢復本輪應保留的行為，不能跳過失敗繼續累積變更；不自動 reset／clean 或丟棄既有修改。
   - 發現需要改業務規則、共用契約、schema、資料／權限或擴大 scope：回原流程做影響與授權判斷；涉及規格變更時沿[規格驅動開發](規格驅動開發.md)確認及安排重驗，該部分不再當成行為不變的重構。值得調整既定規則的建議仍按[調查與分析](調查與分析.md)交有權者裁決。
6. **判斷下一個情境或返回**：本次調用選定的小步／AC 仍有必要情境未完成時，在相同授權與契約內回第 1 步；該小步完成就帶著測試、改動及結果引用返回原流程，先做適用回歸與 review。Task 尚有其他已確認工作，也由原流程的 Loop 選下一輪，不在本次 TDD 調用直接擴展；需改本次 scope 時同樣先返回。
   - 從[開發與變更](開發與變更.md#開發-loop-與回跳)進入：返回其適用驗證及 Loop 分流，再進 review／回寫、下一輪或交付判斷。
   - 從[修復缺陷](修復缺陷.md)進入：返回對照原問題的回歸，保留原因判斷、原失敗及修後 evidence 的區別。
   - 共用模組或跨層影響仍須驗證相應 consumers／業務鏈路；沿用仍適用的已執行結果，不無故重跑。局部 Green 不代替原流程的 required checks、完整 user workflow、deployment 或 acceptance。

## 適用判斷與例外

| 情況 | 判斷與下一步 |
| --- | --- |
| 已確認且已授權的程式行為新增、變更或修復，可安全重複自動判定 | 採用本程序；既有有效測試可以沿用，缺少必要 assertion 時補最小有用測試。 |
| 純文件、格式、唯讀調查、一次性操作 | 不套用 TDD；返回原程序，按實際 claim 選文件核查、人工／工具操作或其他適用驗證。 |
| 無行為變更的 refactor／機械整理 | 先確認必要既有行為與測試基線，整理後做受影響回歸，不強造 Red；發現必要覆蓋缺口時按風險補足。 |
| 缺 runner 或安全 fixture | 先判斷可否在既有授權內建立最小入口／前提；不能只因暫缺工具就略過測試。仍不可用時，必要測試記 NOT_RUN，依下段記錄替代方法或 blocker。 |
| 視覺、硬體、外部依賴、legacy 等無法在本次 scope 安全可靠自動化 | 選實際能支持 claim 的替代證據及回歸，列明限制；若必要驗收仍無法成立，停止依賴它的完成聲明。這是非 test-first 路徑，不能把人工或等價失敗證據叫作 Red。 |
| 只有 log／runtime 等可信既有觀察，尚無 automated failure | 先評估能否據此建立本輪 automated Red；能安全建立時先測再修，既有觀察本身不構成略過 TDD 的例外。無法安全建立時依相應替代路徑記錄。 |
| 接手本輪前目標改動已完成，或有權決定已允許緊急先修後測 | 保留當時證據，按仍有效的授權驗證／補測，說明先後順序及風險；仍需新增的行為變更另按 TDD 適用條件判斷。不冒稱 test-first，不為補造 Red 回退工作樹；需另行風險接受時交有權 owner，「緊急」不新增授權。 |
| 本輪本應採 TDD，卻在沒有有效例外下先行實作 | 如實記方法偏差、原因、改動與尚缺的證據，補必要測試／回歸，保留風險並回原流程判定後續處置；不補造 Red，不把「已完成」當成事後自動豁免，也不豁免後續小步。 |
| 已授權探索／PoC 尚無穩定契約 | 在具名實驗範圍及成功條件內選方法；採納為正式功能前回原流程確認契約、適用 TDD 與必要回歸，不把探索結果直接當 production acceptance。 |

例外／不適用判斷留在原 Task／Issue／VR 的方法或限制欄位：記 scope、理由、決定者／授權依據、替代 evidence、未驗風險及恢復自動化／重議條件（如適用）。工作標準已涵蓋且授權不變的選擇可由執行者記錄，不逐次另求批准；若要放寬項目 mandatory gate、接受新重大風險或改契約／權限，依[工作標準](../規則與標準/工作規則與標準.md#一協作決策與變更)交相應 decision authority。替代路徑不會取消原有驗收義務。

## 輸出與驗證

沿用原工作紀錄及 native run／VR，保留本輪契約／AC、source 與測試身份、實際方法、Red 的原因及先後順序、Green／重構後結果、例外與未驗範圍。結果枚舉及 provenance 依[工作標準](../規則與標準/工作規則與標準.md#結果與狀態)，不另建 TDD 台帳，不要求每輪 commit、全量 suite 或為形式新增測試。

審閱時核對 assertion 能攔截目標契約偏差、實際執行了所聲稱的分支、production change 在有效授權內，且原流程需要的 consumers／鏈路回歸未被局部 Green 省略。按實際 scope 說明是否 test-first；事後補測、只有初始編譯錯誤或替代人工證據均不足以宣稱完成 test-first TDD。

## Failure、stop 與 recovery

契約不明、必要前提／授權缺失或失敗原因反覆不清時，保留目前 source、候選判斷與 run，停止依賴該未知的變更並返回原流程／調查；其他已授權且獨立的部分可繼續。測試 setup、reproduction 或 recovery 涉及刪除、覆寫取代、資料重置或外部寫入時，仍依[破壞性操作](../規則與標準/工作規則與標準.md#破壞性操作)及全部適用 gate，不為取得 Red／Green 擴權或使用真實敏感資料。

## 最小回寫與 Exit

測試資產與必要程式改動回各自 owner；契約變更先由原流程取得確認，再同步 current owners；單次結果及方法限制留原紀錄。Exit 明列完成的小步、Green 支持的 claim、未驗／blocked／例外與返回哪個原流程；只有該流程所需 evidence 齊備才能完成整體工作，不能由 TDD 子循環自行結束原 Issue 或宣稱已交付。
