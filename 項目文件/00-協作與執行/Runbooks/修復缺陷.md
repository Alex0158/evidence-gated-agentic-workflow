# Runbook：修復缺陷

## Trigger 與邊界

當觀察到可描述的失敗，且它相對適用的已確認 contract／acceptance 有差異時使用。沒有已確認 expected behavior 的新想法不是 defect。修復不得只為讓 tests 通過而改產品規格；超出原有修復授權的變更先回 owner。

## 讀者與前提

Defect／issue owner、相應產品／技術 owner、實作者與 reviewer 讀取：適用 current requirement／decision、[項目文件來源目錄](../../README.md)、[項目工程入口](../項目工程入口.md)、協作／工程／evidence 標準、失敗的實際 evidence 及必要 fixture/environment 前提。確認是否允許重現、修改 source、資料或外部服務；沒有明確安全 fixture 時不以真實資料做破壞性重現。

## 按需檢查

- 失敗發生在哪個 source、assertion、fixture、environment、runtime 或使用者觀察層？
- 正式 expected behavior 的 owner、scope、revision 和確認依據是甚麼？
- 可用哪些安全前提重現？哪個步驟與結果是可觀察的？
- 根因支持 defect、test/verifier error、fixture/environment、doc drift、新需求、非缺陷或 accepted risk 哪一類？
- 本次授權涵蓋定位、修改、回歸、資料補救或部署到哪一層？

## 操作程序與分支

1. **界定 claim 並記錄失敗**：先依[工作標準的 Claim 與 evidence path](../規則與標準/工作規則與標準.md#claim-與-evidence-path)確定所要修復的是使用者流程、API/security contract 或其他 claim；保存觸發條件、source/artifact revision、環境、輸入、實際 command／步驟、expected／observed 與 evidence。API security 問題即使沒有 UI caller 也須按 direct API/server guard 路徑查證；API 結果不能替代完整 user workflow。未能重現時標未知或 flaky candidate，不虛構一致性。
2. **核對正式預期**：從 canonical requirement、business rule、decision 及確認 event 確定預期。如果只有 proposal／未確認內容，停止以 defect 名義改行為，轉為需求釐清；需要提出產品／技術內容時按 scope 使用[模組與功能規格範本](../../../文件模板/模組與功能規格範本.md)或[技術設計與契約範本](../../../文件模板/技術設計與契約範本.md)。
3. **定位原因並標明證據強度**：檢查實際 source、assertion、fixture／依賴／環境與 verifier 是否覆蓋相同條件。在既有 Issue／Task 調查摘要保留候選原因、支持／反證、信心與未決，實際觀察引用原 run。推翻某個原因不代表原問題不存在；無法安全重現時可引用可信的既有失敗證據並明示限制，不為修復強造一次危險的修前 FAIL。
4. **選分類**：
   - 證據不足／原因未明：保留候選判斷及下一個最小查證，按既有授權回[調查與分析](調查與分析.md)或適用驗證分支；不把假設當既定原因，其他無依賴且已授權的工作可繼續。
   - Product defect：source 違反 current contract，進入最小 source 修正。
   - Test/verifier defect：測試沒有檢查 contract 或自身判定錯；只有 evidence 支持且有授權才修 asset。
   - Fixture/environment/tooling issue：不改產品邏輯，先修可重建前提或以 NOT_RUN／blocked handoff；按工作標準[結果與狀態](../規則與標準/工作規則與標準.md#結果與狀態)將工作狀態與 cause／owner 分開記錄。
   - 資料 source／欄位可改性不明：依工作標準[資料來源與表示權威](../規則與標準/工作規則與標準.md#資料來源與表示權威)追查，未查清前不把 request value 當權威；產品／業務 owner 裁定語義，技術／native owner 承接表示。
   - Documentation drift：修 primary 文檔或 stale summary；若 code 偏離 approved contract，不能直接把 code 當新規則。
   - New requirement：留下 proposal／decision need，等適用 owner 確認。
   - Accepted risk：必須有適用的有權事件；保留原缺陷／未驗／未知身份，引用接受範圍、責任及適用的期限／恢復條件。不因風險被接受而改驗收、標已修或補 PASS；若決定真正改變產品行為，轉[開發與變更](開發與變更.md)同步 current owners，保留原歷史。處置留既有 tracker／決策來源，不新增台帳。
   - Non-defect／accepted behavior：引用能支持本 scope 判斷的 evidence 及適用正式例外／contract，記清使用情境，不把它列為已修。
5. **實施最小修正**：僅在授權內改根因 owner；不刪 evidence、不改需求以迎合 test、不順手擴 scope。若涉及 schema／API／types，沿[開發與變更](開發與變更.md)的 native handoff 條件逐 owner 交接。任何方案若需要刪除、覆寫取代、reset／clean 或 destructive data step，按[破壞性操作](../規則與標準/工作規則與標準.md#破壞性操作)與[本項目 AGENTS.md](../../../AGENTS.md)通過兩道 gate，執行前重解並核 exact targets；不能因修復技術需要推定獲授權。
6. **對照原問題做回歸**：沿[驗證功能](驗證功能.md)選方法，優先判定原失敗的正式預期、關鍵輸入／條件與必要 forbidden effects，再按風險補 consumer／鏈路檢查。在既有工作摘要連接原失敗 evidence／基線、修正範圍及修後對應 check；沒有可用原 run 時明示實際依據，不虛構。行為改善的 assertion 與支持根因的證據分開，一個修後 PASS 不自動證明因果或完整原鏈路。必要 runner／前提缺少的檢查保留 NOT_RUN；已完成人工／工具核查只支持其 claim。結果留原 VR／native run，其他位置引用，不強制每次新建測試或整套 E2E。
7. **重開條件**：若根因假設被否定、回歸仍失敗、新 evidence 擴大影響，或風險接受的適用期限／條件已失效，重新分類或交有權 owner 處理；保留之前 run，不把舊 FAIL 改成新 PASS。

## 輸出與驗證

輸出需分清原問題分類、原因判斷／信心與 evidence、修正或風險處置，並連最小修正 owner、受影響 consumer、原失敗與修後 check、未驗證範圍、task 狀態及 reopen 條件。修復後的 source 與 current contract 一致，assertion 判定正式預期，而不是方便預期。

Code fixed、environment pending、regression NOT_RUN、部分完成和未部署可以同時成立；只報告本次已證明的層次。

## Failure、stop 與 recovery

無法安全重現、缺正式預期、資料 ownership 不明，或必要授權／風險決策／安全前提／適用 gate 未滿足時，停止相依動作並明示 blocker；其他可獨立查證按既有授權繼續。需要重置或涉及權限／相容性／資料政策時，先核本次 scope、已有決策與全部適用 gate；條件齊備後才可按授權程序恢復，不因「需要重置」便永久 blocked，也不以一般修復授權代替新政策或外部操作權。依工作標準分開 result／state 與 cause／owner，並核 gate 本身是否為本次承諾。破壞性路徑仍遵循[破壞性操作](../規則與標準/工作規則與標準.md#破壞性操作)的完整規則，執行前重核 exact target list。

若修改失敗或造成新差異，保留當前工作與 log；根據項目已授權的 recovery procedure 處置。沒有明確補救步驟時不 reset／clean／刪除；停止擴大影響並 handoff 到有權 owner。

## 最小回寫與 Exit

正式預期回產品／技術 owner，修正回 native source 或正確文檔 owner，單次失敗與回歸回原 issue／verification record。只更新受影響摘要／索引。Exit 時明列分類、修正、回歸結果、NOT_RUN／blocked、剩餘風險與 reopen 條件；只有原始 claim 所需 evidence 齊備才 close。
