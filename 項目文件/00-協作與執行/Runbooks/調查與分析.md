# Runbook：調查與分析

## Trigger 與邊界

當問題、source conflict、行為差異、資料狀態或失敗原因尚不清楚時使用。調查的完成結果可以是 evidence 整理與待決項；程序本身不新增修復、發布、部署或產品決策權。若原始任務已明確授權後續變更，可在分類後轉到相應 Runbook。

涉及功能行為、跨步業務結果或共用模組，或需要提出修復／優化方案時，先理解相關業務鏈路與共用影響，再比較方案，避免局部改善損害其他鏈路。分析深度以會改變判斷的實際影響為界；單純文字、格式或無業務影響的局部查證可簡述適用範圍與理由，不強造完整鏈路圖、選項表或全庫盤點。

## 讀者與前提

要求者／問題 owner、相關產品或技術 source owner、maintainer 和調查 Agent 依問題讀取：[項目文件來源目錄](../../README.md)、目標 current contract、[項目工程入口](../項目工程入口.md)，以及必要的協作／工程／evidence 標準和既有 issue／task／verification record。先確認本次只允許 read-only，還是另有具名的受控查證授權，以及允許查閱的 repo／資料／環境與 evidence 保存位置；不查詢未授權的真實資料或秘密。主動重現按下方分支轉驗證，不由調查程序取得新操作權。

## 按需檢查

- 要驗證或排除哪一個具體假設？涉及哪個功能、業務模組／目標及實際鏈路？
- 共用程式、規則或資料還被哪些業務使用？方案會改變它們的結果、契約或副作用嗎？
- 推薦方案為何較有利於整體項目？是否有值得調整既定規則、功能或定位的選項需要提出給決策者？
- current、intended、observed 分別由哪個 owner 和 revision 支持？
- 我在調查、修復、產品採納還是 runtime acceptance？本次授權到哪一層？
- 找不到 evidence 是因 source 缺失、搜尋範圍不足，還是已在明確範圍證明不存在？
- 哪一個最小反例或觀察能改變結論；它針對原問題、某個原因假設，還是驗證方法？哪個未知真的阻塞下一步？

## 操作程序與判斷分支

1. **界定問題與 claim**：將原始描述轉成可觀察差異，標明觸發、scope、版本／環境和影響。分清報告者自述、可重現事實、假設及未知；按工作標準[Claim 與 evidence path](../規則與標準/工作規則與標準.md#claim-與-evidence-path)先說明這次要證明甚麼。
   - 任何階段發現影響目標、安全／資料、核心／共用鏈路、scope 外後續工作或可能遺失 evidence 的重要事項時，按[任務登記與分流](任務登記與分流.md)作有界查重／最小捕捉；查重不足或主源不可用時可先在允許位置保存為待查重／待登記，再對帳補齊，不等第 9 步或根因已明。寫入權不足時依該程序交安全 handoff，不把唯讀調查擴為 tracker 寫入或修復；已派送但結果未知的登記仍保留待對帳，不改判未寫入。
2. **盤點 source**：透過[項目文件來源目錄](../../README.md)定位 primary owner；記錄實際讀取的路徑／revision、文件身份、適用 scope 與缺漏。對 code、規格、decision、assertion、runtime observation 分別說明它能證明甚麼。
3. **還原 current 與 intended**：從適用確認事件讀 expected behavior；從指定 native source 讀 actual implementation；只在本次有 runtime evidence 時陳述 observed behavior。若問題涉及 API security，即使沒有 UI caller，也核對後端 route／handler 與 server-side guard，並以符合該 claim 的 direct request evidence 查證；API evidence 只支持 API claim，不替代使用者流程。要證明完整 user workflow，另追實際入口到可觀察結果。不要拿 template、generated 視圖或歷史記錄當現行契約。
4. **理解業務鏈路與共用影響**：先定位功能要達成的業務結果、所屬業務模組及其 owner；業務模組依概念／規則責任判斷，不由頁面、service 或程式目錄一對一推定。
   - 沿相關入口／觸發、角色與資格、規則、狀態／資料轉移、handoff 及副作用，追到可觀察的業務結果；分清規格描述、source 所示路徑與本次實際觀察。
   - 連到實際 code／API／event／schema／資料依賴；涉及共用程式、規則、設定或資料時，追查直接及必要的間接 consumers，定位它們承接的其他業務鏈路／模組，以及必須保留的行為、相容性、資料與權限契約。不要只憑修好眼前功能推定整體無影響。
   - 沿實際依賴及有依據的候選影響關係擴展，記錄已查範圍、重要未知及停止依據；未查清的共用影響不能寫成「沒有影響」。既有分析可在核實 scope／revision／依賴仍適用後引用，不重做整份文件。
5. **依授權查證假設與反例**：先說清這個觀察能支持／推翻哪一項假設；原問題的成立程度與原因判斷分開保留。方法及結果依[工作標準](../規則與標準/工作規則與標準.md#結果與狀態)，不另定結果枚舉。
   - 唯讀查證：先核操作效果符合本次唯讀 scope；需要 native runner 時核[項目工程入口](../項目工程入口.md)的實際入口，缺少必需 runner 的檢查記 NOT_RUN。人工／工具或 source 核查記實際方法、scope 及 evidence，不抹去已完成的觀察，也不發明命令。
   - 需要主動重現／狀態變更時：可在分類前轉[驗證功能](驗證功能.md)，先核該動作已有授權、隔離前提及全部適用 gate，再按允許範圍查證。只有唯讀授權或條件不足時停止該操作，繼續可獨立的 source 調查並交接缺口；direct request 的證據需求不是唯讀豁免。
   - 取得驗證結果後：引用原 run 回到本調查更新假設／分類。結果只支持實際檢查的 claim，查證授權不等於產品修復權；已有後續修復授權則繼續按其 scope 分流。
6. **追資料權威（如有歧義）**：依工作標準[資料來源與表示權威](../規則與標準/工作規則與標準.md#資料來源與表示權威)沿實際處理鏈查清欄位的來源和可改性。未能查清時保留 ambiguity 並停止依賴該結論的動作；產品／業務 owner 裁定意義，技術／native owner 承接表示。需要新增／修訂產品或技術內容時，再按本程序所涉內容選用[模組與功能規格範本](../../../文件模板/模組與功能規格範本.md)或[技術設計與契約範本](../../../文件模板/技術設計與契約範本.md)。
7. **分類結果**：
   - accepted contract 與實際 source／可回查觀察不一致：candidate defect，保留兩者並按授權走[修復缺陷](修復缺陷.md)；不由此預定根因在程式、資料或環境哪一層。
   - contract 已變而摘要／指引未更新：doc drift，指出 primary owner 與受影響摘要。
   - 新輸入要求改變行為：new requirement；放在 proposal／source disposition，不偽裝成 bug fix。
   - command／fixture／外部依賴無法成立：environment／fixture gate，記錄受阻 claim、cause 和 owner，並按[工作標準的結果與狀態](../規則與標準/工作規則與標準.md#結果與狀態)分開表達；若 gate 本身屬本次承諾，另定對應 claim 查證。
   - source 互相矛盾或確認權不明：decision gap，列出需要 owner 裁決的範圍。
   - 某個原因假設被反證推翻：保留原問題的成立／待證狀態，回第 5 步選下一個最小查證；不直接判為 non-defect。
   - 原問題前提在指定 scope 被可靠證據否定，或行為符合適用 contract／已確認例外：才作該 scope 的非缺陷或 accepted behavior 判斷，連回正式 owner 及支持證據。
   - 證據不足或原因仍未明：保留 unknown／候選判斷、限制與下一個最小查證，不以未重現或未找到原因代表問題已消失。
8. **比較方案並提出推薦（需要處置建議時）**：先以整體項目目標、業務結果及有效約束判斷方案，不只以局部症狀消失、修改行數或眼前測試通過作選擇。
   - 比較真正可行的選項；按問題考慮局部修正、共用根因修正、維持現況／延後等，不強造無意義選項。說明各方案對原鏈路及其他 consumers 的收益、代價、維護負擔、相容／遷移影響、風險、重要未知和所需驗證；已有 evidence 直接引用。簡單取捨可短答，重要且需追溯的決定才用[決策範本](../../../文件模板/決策範本.md)。
   - 若 evidence 顯示修改核心文件已定義的規則、功能或產品定位可能更合理，Agent 應主動提出該選項，說明現有假設的問題、支持／反證、預期整體收益、受影響 owners／鏈路、成本與驗證方法，交由有權的使用者／產品決策者決定。不得只為符合舊規則隱藏較佳選項，也不得以建議代替批准。
   - 明列推薦理由、未選選項及待裁決事項；只主張目前證據與約束下較合理的方案，不宣稱絕對最優。既有行為即使符合 contract，仍可另提改善 proposal；即使建議改 contract，已觀察到的偏差也不能因此消失。未確認前保留 current contract、原問題分類與未解風險，不自行調低驗收或擴大實作。
9. **後續工作處置與下一步**：轉出或 Exit 前，對每項重要 finding 明確判斷下列處置，並按[任務登記與分流](任務登記與分流.md)及[工作任務範本](../../../文件模板/工作任務範本.md)分階段補齊，不複製整份分析：
   - 已有對應任務／Issue：更新原項的問題、業務／共用影響、已證／未證、關鍵 evidence、建議／待決及下一步，引用本次分析與主源，不重複登記。
   - 需要後續行動／決策而尚無對應項：有界查重後建立最小待處理項；重要發現可先按待查重分支捕捉，再安排暫定分類、優先級評估、責任及 Route。主源未成立或確認未寫入時保留待登記／handoff；已派送未明則保留登記結果未知、操作 reference 及對帳下一步，不宣稱已進 backlog 或被接手。
   - 已在本次處理完成：回寫原工作及必要驗證 reference，依該 instance 的完成層判斷；不另建已解決待辦，也不由調查／Task 完成自動 close 原 Issue。
   - 有依據判斷無後續處理需要：保留 scope、結論／理由及適用重開條件，不強造新 Task。Unknown、未重現或未查出原因本身不足以作這個判斷；需延後／接受風險的部分依有權處置記錄。

只有既有授權覆蓋的修復才進[修復缺陷](修復缺陷.md)或[開發與變更](開發與變更.md)；verify-only 進[驗證功能](驗證功能.md)；交付需求進[版本交付](版本交付.md)。契約待釐清或 proposal 涉及規格變更時沿[規格驅動開發](規格驅動開發.md)處理確認、primary owner 回寫及重驗安排，再依授權銜接變更與驗證；不把決策紀錄當成完整 current spec。若無授權，只交付調查和具體 handoff；不因找出原因、推薦方案或登記任務而自動實作。

## 輸出與驗證

建立精簡的調查結果或更新既有 tracker，包含問題與影響、搜尋範圍、讀取來源／revision、事實、原因假設及其支持／反證、未知、分類、決策者及下一個最小行動。原問題、原因判斷及處置分清；實際觀察引用原 VR／native run，不複製完整結果。已有對應記錄就沿用，不強造新文件。

後續處置引用實際已更新／新登記的主源；尚未登記／承接、待決／延後或無需新增的部分說明理由、下一責任與行動。途中已入主源的項目回原項補 evidence；只有暫存捕捉時，按登記程序對帳、readback 後轉指主源並停止續寫同維度狀態，不再從收尾另建一份。後續 Task 摘要與完整分析保持引用關係。

涉及業務／共用影響或處置建議時，另保留功能／模組／鏈路及共用 consumers 的定位、影響邊界、方案取捨、推薦依據、必要驗證與待裁決的契約變更。對推薦方案說明原問題及其他受影響鏈路要如何驗證；需要但尚未執行的檢查記 NOT_RUN，有意省略時依工作標準記 SKIP 及理由，不把影響分析當成回歸通過。審閱時核對是否先有業務脈絡與共用影響依據、再有推薦，以及 proposal 與確認事件是否分清；不需重複完整分析或新增台帳。

驗證報告中的每一項結論都能回到直接來源；未找到與不存在分開；推論標出推論；NOT_RUN 不寫成 PASS。結論只限已檢查的 repo、revision、環境和時間，不外推到未看的資料或部署。

## Failure、stop 與 recovery

查證超出允許 scope、涉及未授權資料／帳戶／環境操作，或安全前提及適用 gate 未滿足時，停止相依查詢並記錄缺口；不要用更寬權限或 production data 繞過。已有受控查證授權時仍按第 5 步的驗證分支操作，不能留在唯讀模式卻直接寫入。來源在 scope／baseline 不匹配時先停下該結論並回[項目文件來源目錄](../../README.md)找適用 owner。若任何查證、恢復方案或外部步驟需要刪除／reset／覆寫，按[破壞性操作](../規則與標準/工作規則與標準.md#破壞性操作)套用 global／project 兩道 gate，執行前重核 exact target list；不確定時保留現狀並 handoff。重複搜尋沒有新 evidence 時依明確 coverage 停止，不用擴大到不相關 repo。

如果中途發現錯用 source，保留已有結果並標記撤回或更正原因；不要無痕改寫舊結論。修復或決策無法安全回復時停止依賴部分、保留現有狀態並 handoff；不要自動 reset／刪除。

## 最小回寫與 Exit

穩定產品／技術規則只回其 owner；一次調查觀察留在 dated record；需要重新分類時連結後續 Runbook。更新有失效的入口或引用，不複製完整分析到標準／規格。Exit 時明列已證、未證、阻塞、非本次 scope、後續工作處置及下一責任人；若仍未知但已回答原調查目標，可完成該調查 instance，仍需保留後續追蹤／handoff，不把 unknown 當非缺陷、已修復或原 Issue 自動結束。
