# Runbook：調查與分析

## Trigger 與邊界

當問題、source conflict、行為差異、資料狀態或失敗原因尚不清楚時使用。調查的完成結果可以是 evidence 整理與待決項；程序本身不新增修復、發布、部署或產品決策權。若原始任務已明確授權後續變更，可在分類後轉到相應 Runbook。

## 讀者與前提

要求者／問題 owner、相關產品或技術 source owner、maintainer 和調查 Agent 依問題讀取：[項目文件來源目錄](../../README.md)、目標 current contract、[項目工程入口](../項目工程入口.md)，以及必要的協作／工程／evidence 標準和既有 issue／task／verification record。先確認本次只允許 read-only，還是另有具名的受控查證授權，以及允許查閱的 repo／資料／環境與 evidence 保存位置；不查詢未授權的真實資料或秘密。主動重現按下方分支轉驗證，不由調查程序取得新操作權。

## 按需檢查

- 要驗證或排除哪一個具體假設？影響對誰／哪條鏈路？
- current、intended、observed 分別由哪個 owner 和 revision 支持？
- 我在調查、修復、產品採納還是 runtime acceptance？本次授權到哪一層？
- 找不到 evidence 是因 source 缺失、搜尋範圍不足，還是已在明確範圍證明不存在？
- 哪一個最小反例或觀察能改變結論；它針對原問題、某個原因假設，還是驗證方法？哪個未知真的阻塞下一步？

## 操作程序與判斷分支

1. **界定問題與 claim**：將原始描述轉成可觀察差異，標明觸發、scope、版本／環境和影響。分清報告者自述、可重現事實、假設及未知；按工作標準[Claim 與 evidence path](../規則與標準/工作規則與標準.md#claim-與-evidence-path)先說明這次要證明甚麼。
2. **盤點 source**：透過[項目文件來源目錄](../../README.md)定位 primary owner；記錄實際讀取的路徑／revision、文件身份、適用 scope 與缺漏。對 code、規格、decision、assertion、runtime observation 分別說明它能證明甚麼。
3. **還原 current 與 intended**：從適用確認事件讀 expected behavior；從指定 native source 讀 actual implementation；只在本次有 runtime evidence 時陳述 observed behavior。若問題涉及 API security，即使沒有 UI caller，也核對後端 route／handler 與 server-side guard，並以符合該 claim 的 direct request evidence 查證；API evidence 只支持 API claim，不替代使用者流程。要證明完整 user workflow，另追實際入口到可觀察結果。不要拿 template、generated 視圖或歷史記錄當現行契約。
4. **依授權查證假設與反例**：先說清這個觀察能支持／推翻哪一項假設；原問題的成立程度與原因判斷分開保留。方法及結果依[工作標準](../規則與標準/工作規則與標準.md#結果與狀態)，不另定結果枚舉。
   - 唯讀查證：先核操作效果符合本次唯讀 scope；需要 native runner 時核[項目工程入口](../項目工程入口.md)的實際入口，缺少必需 runner 的檢查記 NOT_RUN。人工／工具或 source 核查記實際方法、scope 及 evidence，不抹去已完成的觀察，也不發明命令。
   - 需要主動重現／狀態變更時：可在分類前轉[驗證功能](驗證功能.md)，先核該動作已有授權、隔離前提及全部適用 gate，再按允許範圍查證。只有唯讀授權或條件不足時停止該操作，繼續可獨立的 source 調查並交接缺口；direct request 的證據需求不是唯讀豁免。
   - 取得驗證結果後：引用原 run 回到本調查更新假設／分類。結果只支持實際檢查的 claim，查證授權不等於產品修復權；已有後續修復授權則繼續按其 scope 分流。
5. **追資料權威（如有歧義）**：依工作標準[資料來源與表示權威](../規則與標準/工作規則與標準.md#資料來源與表示權威)沿實際處理鏈查清欄位的來源和可改性。未能查清時保留 ambiguity 並停止依賴該結論的動作；產品／業務 owner 裁定意義，技術／native owner 承接表示。需要新增／修訂產品或技術內容時，再按本程序所涉內容選用[模組與功能規格範本](../../../文件模板/模組與功能規格範本.md)或[技術設計與契約範本](../../../文件模板/技術設計與契約範本.md)。
6. **分類結果**：
   - accepted contract 與實際 source／可回查觀察不一致：candidate defect，保留兩者並按授權走[修復缺陷](修復缺陷.md)；不由此預定根因在程式、資料或環境哪一層。
   - contract 已變而摘要／指引未更新：doc drift，指出 primary owner 與受影響摘要。
   - 新輸入要求改變行為：new requirement；放在 proposal／source disposition，不偽裝成 bug fix。
   - command／fixture／外部依賴無法成立：environment／fixture gate，記錄受阻 claim、cause 和 owner，並按[工作標準的結果與狀態](../規則與標準/工作規則與標準.md#結果與狀態)分開表達；若 gate 本身屬本次承諾，另定對應 claim 查證。
   - source 互相矛盾或確認權不明：decision gap，列出需要 owner 裁決的範圍。
   - 某個原因假設被反證推翻：保留原問題的成立／待證狀態，回第 4 步選下一個最小查證；不直接判為 non-defect。
   - 原問題前提在指定 scope 被可靠證據否定，或行為符合適用 contract／已確認例外：才作該 scope 的非缺陷或 accepted behavior 判斷，連回正式 owner 及支持證據。
   - 證據不足或原因仍未明：保留 unknown／候選判斷、限制與下一個最小查證，不以未重現或未找到原因代表問題已消失。
7. **選擇下一步**：只有既有授權覆蓋的修復才進[修復缺陷](修復缺陷.md)或[開發與變更](開發與變更.md)；verify-only 進[驗證功能](驗證功能.md)；交付需求進[版本交付](版本交付.md)。若無授權，只交付調查和具體 handoff；不因找出原因而自動實作。

## 輸出與驗證

建立精簡的調查結果或更新既有 tracker，包含問題與影響、搜尋範圍、讀取來源／revision、事實、原因假設及其支持／反證、未知、分類、決策者及下一個最小行動。原問題、原因判斷及處置分清；實際觀察引用原 VR／native run，不複製完整結果。已有對應記錄就沿用，不強造新文件。

驗證報告中的每一項結論都能回到直接來源；未找到與不存在分開；推論標出推論；NOT_RUN 不寫成 PASS。結論只限已檢查的 repo、revision、環境和時間，不外推到未看的資料或部署。

## Failure、stop 與 recovery

查證超出允許 scope、涉及未授權資料／帳戶／環境操作，或安全前提及適用 gate 未滿足時，停止相依查詢並記錄缺口；不要用更寬權限或 production data 繞過。已有受控查證授權時仍按第 4 步的驗證分支操作，不能留在唯讀模式卻直接寫入。來源在 scope／baseline 不匹配時先停下該結論並回[項目文件來源目錄](../../README.md)找適用 owner。若任何查證、恢復方案或外部步驟需要刪除／reset／覆寫，按[破壞性操作](../規則與標準/工作規則與標準.md#破壞性操作)套用 global／project 兩道 gate，執行前重核 exact target list；不確定時保留現狀並 handoff。重複搜尋沒有新 evidence 時依明確 coverage 停止，不用擴大到不相關 repo。

如果中途發現錯用 source，保留已有結果並標記撤回或更正原因；不要無痕改寫舊結論。修復或決策無法安全回復時停止依賴部分、保留現有狀態並 handoff；不要自動 reset／刪除。

## 最小回寫與 Exit

穩定產品／技術規則只回其 owner；一次調查觀察留在 dated record；需要重新分類時連結後續 Runbook。更新有失效的入口或引用，不複製完整分析到標準／規格。Exit 時明列已證、未證、阻塞、非本次 scope 及下一責任人；若仍未知但已回答原調查目標，可完成該調查 instance，不把 unknown 當非缺陷、已修復或原 Issue 自動結束。
