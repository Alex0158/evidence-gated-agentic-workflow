# Runbook：開發與變更

## Trigger 與邊界

用於在既有確認需求／技術契約及明確授權內新增或調整功能、文件或工程行為。重大產品方向、權限／資料政策、相容性或外部承諾未確認時，不把實作當成批准。純調查走[調查與分析](調查與分析.md)；觀察到相對 current contract 的失敗走[修復缺陷](修復缺陷.md)；單獨驗證走[驗證功能](驗證功能.md)。

也適用於已明確授權的隔離實驗：先固定實驗假設、允許動作、資料／環境邊界及停止條件，再按本程序實作。實驗規格只在該 scope 生效，client acceptance 與 production readiness 仍各自判定；不以一般產品確認缺席撤銷已給予的實驗授權。

## 讀者與前提

執行者、產品／技術 canonical owners、maintainer 和 reviewers 按 scope 閱讀：[項目文件來源目錄](../../README.md)、具體 accepted requirement／business rule、必要設計／decision、[工作標準](../規則與標準/工作規則與標準.md)、[項目工程入口](../項目工程入口.md)以及適用 tracker。先核對 active repo、source root、protected repo、baseline、runner 與 environment。工具值僅從唯一 binding 取得，不在 task 或本程序複製。

## 按需檢查

- 這是已確認範圍內深化、doc drift、defect 修復，還是新產品要求？
- 哪個 owner 定義行為／契約？它的 scope、確認事件和 revision 是甚麼？
- 受影響的角色、資料、狀態、read/write、副作用、consumer 與相容性是甚麼？
- 要改的 native owner 已綁定嗎？若沒有，MD contract 是否仍是唯一技術定義？
- 要支持甚麼 claim？有哪些必要驗證與環境前提？
- 哪個未知會阻止安全實作，哪部分仍可獨立推進？

## 開發 Loop 與回跳

本檔統籌完整主循環；SDD 管本輪規格／契約的核對、變更與就緒，TDD 管適用行為的小步實作。沿用仍有效的前提及結果，不將每次循環變成重新啟動項目或重建全部文件。

**目標與授權 → 業務鏈路／共用影響及方案比較 → SDD 核對／確認規格 → 必要設計與小步安排 → TDD 或適用替代路徑 → 整體驗證 → Review／最小回寫 → 下一輪或交付。**

| 當輪結果 | 回跳與下一步 |
| --- | --- |
| 契約清楚，實作未滿足它 | 按授權進[修復缺陷](修復缺陷.md)或返回本輪 TDD，保留失敗 evidence，不改規格迎合 code。 |
| 規格／AC 有歧義、缺漏或值得調整 | 返回本流程的 SDD 階段；原因／影響未明先調查。規格實質變更後重核影響、設計、小步及驗證，不從舊 Green 直接跳到交付。 |
| Test/verifier、fixture／environment 或工具失敗 | 按[驗證功能](驗證功能.md)分類並修正獲授權的正確 owner，必要時調查；不預定是產品缺陷，也不略過 required checks。 |
| 未具備本輪必要授權／前提，或驗證尚未完成 | 只停止依賴部分，保留 partial／blocked／NOT_RUN、解除條件及責任人；其他已授權且獨立的小步可繼續。 |
| 當輪通過，仍有本次 scope 內的已確認工作 | 回到必要設計與小步安排，核規格及 evidence 是否仍適用；目標／scope／風險變化則先重核邊界，重大方向重定向轉[啟動項目](啟動項目.md)。 |
| 本次目標及必要檢查已滿足 | 完成 review／回寫；只有已授權的交付需求才進[版本交付](版本交付.md)，否則交付實際完成層及後續 owner。 |

## 操作程序與分支

1. **固定 scope**：記錄工作目標、允許動作、primary requirement、source revision、驗收 owner、repo/source root 與明確 non-goals。若只在已確認條款內細化，沿用其確認事件，不另造批准。
2. **處理內容身份**：
   - 需求已確認且變更在其範圍內：沿用確認依據，進入下方影響分析與必要設計，不在此分支先行實作。
   - 已授權隔離 PoC：引用唯一實驗授權／假設 owner，建立可判定 AC，再依下方影響、設計及驗證安排推進；未知只阻塞真正依賴它的部分。
   - 只發現文件摘要或指引落後：先按 source owner 更新必要文檔，核 affected references。
   - 新輸入會改變 current 行為：保留 proposal，取得適用決策後才更新 current 或擴大實作。
   - 方向／權限／資料／相容性有重大未知：停止依賴部分，列具體決策；其他已授權獨立部分可繼續。
3. **做影響分析**：沿用並核實[調查與分析](調查與分析.md#操作程序與判斷分支)中的業務脈絡、共用影響與方案取捨是否仍適用；沒有既有分析時，在本次工作補足必要部分，不強制另開調查或重寫紀錄。沿正向來源找真正的 consumer、業務模組／鏈路、API／event／schema、UI、tests、資料與 side effects；共用模組的其他使用方及其契約也納入影響範圍。若發現更合理但需調整既定規則、功能或定位的方案，依該 Runbook 提出待裁決建議，不以實作逕行採納。資料來源／欄位可改性不清楚時，依工作標準[資料來源與表示權威](../規則與標準/工作規則與標準.md#資料來源與表示權威)追查並保留 unresolved ambiguity；產品／業務 owner 決定語義與可改性，技術／native owner 承接實際表示。只讀必要範圍；派生關係視圖過時時回 primary owner 校對，不要求全庫掃描。
4. **SDD、必要設計與小步安排**：
   - 依工作標準[SDD 適用與規格變更](../規則與標準/工作規則與標準.md#sdd-適用與規格變更)進[規格驅動開發](規格驅動開發.md)，完成沿用／補缺／確認、開工條件及重驗安排後返回本階段。已確認契約足夠就引用短路徑；未決只阻塞依賴它的工作，SDD 就緒不新增實作權。非適用或具名 PoC 依其分支記範圍與限制，不強造完整 spec。
   - 尚未建立 native schema／types／API definition 等 owner：已確認 MD 可承接正式技術設計；明確表示 native source 未存在，不發明 command 或影子 binding。
   - 計畫從 MD handoff 至 native owner：先逐 artifact／欄位組列原／新 owner、location、scope、baseline 及所需確認；實作後核新 source 可達、必要語義與相容性已完整承接，才完成交接並把 MD 精確結構降為入口引用。未建立或有未處理偏差的範圍保留 MD authority，不提前宣稱 handoff 完成。
   - 需要新增／修訂產品、業務或技術設計文件時，按內容選用[模組與功能規格範本](../../../文件模板/模組與功能規格範本.md)、[業務流程範本](../../../文件模板/業務流程範本.md)或[技術設計與契約範本](../../../文件模板/技術設計與契約範本.md)；模板提供格式，不取代 owner 或確認事件。
   - 進入實作前，本次 scope 的必要設計、可判定 AC／禁止副作用、最小驗證方法及前提應已可定位；阻塞未知只攔其依賴部分。已有內容直接引用，簡單變更可用幾句說明，不強造 spec／Task／ADR 或整套 tests。需要新 runner 的工作可把建立入口納入已授權計劃，實際未執行的檢查仍保持 NOT_RUN。
   - 沿 SDD 的安排選下一個可獨立驗證的小步，引用其規格／AC、改動 owner、依賴及最小驗證；必要時調整先後次序。每步開始前核條件仍成立，未完成但無依賴的已授權工作可分開推進，不要求逐步重新批准。
5. **實作最小變更**：先依工作標準[TDD 適用與例外](../規則與標準/工作規則與標準.md#tdd-適用與例外)判斷方法；適用時以第 4 步選定的小步／AC 進[測試驅動開發](測試驅動開發.md)完成 Red → Green → Refactor，完成後先返回第 6 步，不在子程序接入 Task 的其他小步。非 TDD 路徑按其條件記理由、替代驗證及限制，不跳過必要驗收。按 native layering 修改本次 active source，保留使用者既有修改，不 reset／clean／刪除。涉及跨 owner 的值時改唯一定義點及其必要 consumers；不在 README、Runbook 或項目工程入口重抄 JSON 精確命令／設定值。若計畫需刪除、覆寫取代、reset／clean 或其他破壞性處置，依[破壞性操作](../規則與標準/工作規則與標準.md#破壞性操作)及[本項目 AGENTS.md](../../../AGENTS.md)完成兩道 gate，執行前重新解析並核 exact target list。
6. **執行適用驗證**：沿[驗證功能](驗證功能.md)執行前一步選定的方法，涵蓋 SDD 已識別的規格變更重驗及本次受影響 consumers／業務鏈路，按實際改動與風險調整必要範圍。TDD 已執行結果仍適用時直接引用，不為切換 Runbook 重跑。需要 native runner 的檢查只用[項目工程入口](../項目工程入口.md)真正存在的入口；缺少時該項記 NOT_RUN。已授權且可獨立完成的人工／工具或 source 核查照其 claim 留 evidence，不冒充缺失的產品測試。結果按上方[回跳條件](#開發-loop-與回跳)分流，不把局部 Green 當整體完成。
7. **Review、最小回寫與下一輪**：檢視實際 diff／狀態、規格與確認引用、compatibility、assertion 及驗證輸出，確認變更仍服務原業務結果且沒有遺漏共用 consumers。穩定內容及一次結果依下方[最小回寫](#最小回寫與-exit)回原 owner；partial implementation 明列完成／未完成／未驗範圍，不用部分結果標整體 Done。尚有本次 scope 內工作時按上方 Loop 選下一步；必要 evidence 齊備才結束本次工作，需要交付時再按授權 Route，不自動 commit／push／deploy。

## 輸出與驗證

輸出是 owner 對齊的最小 source／文件變更、必要的相容性與 consumer 更新，以及綁定實際 revision／command／結果的 evidence。確認其行為沒有因 test assertion 而改寫產品要求；MD/native handoff 有明確 scope 和承接 evidence；所有受影響引用可回到 primary owner。

原 Task／紀錄應足以定位本輪規格／AC、就緒及允許 scope、小步改動、TDD／替代方法、整體驗證、回跳／未決與下一步；已有來源直接引用，不新建平行進度表。SDD 就緒、TDD Green、本次完成與可交付各自保留依據。

發現獨立後續問題、scope 外建議或需交接事項時，按[任務登記與分流](任務登記與分流.md)更新原項或最小登記，重要發現可途中先捕捉；一般小步留原 Task，不因登記擴大本次實作。Review／Exit 核清待辦的主源、責任與下一步，不能以本輪完成隱藏尚未處理項。

Source inspection、build、test execution、runtime 和 acceptance 分別報告。所需 runner 不存在的檢查明寫 NOT_RUN 和原因；只有實際完成且有足夠 evidence 的 assertion／核查才可在其 claim 範圍稱 PASS。

## Failure、stop 與 recovery

若實際 source 與 accepted contract 不符，依上方[回跳條件](#開發-loop-與回跳)在授權內返回本輪 TDD／修正，或走[修復缺陷](修復缺陷.md)分類，不能默默改需求迎合 code。若 test、fixture 或 environment 失敗，分辨其層級再決定是否阻塞本次 claim，並依工作標準分開記錄結果狀態與 cause／owner。若實作暴露新的重大決策、資料安全或不相容影響，保留已完成部分並停止依賴該決定的變更。

預期歧義或規格變更回[規格驅動開發](規格驅動開發.md)，按有權確認及影響重新進入本 Loop；未確認 proposal 不改 current 或原失敗結果。純文件／格式、無行為變更整理及已授權隔離 PoC 按 SDD／TDD 各自的適用與例外處理，不因其中之一不適用而取消另一個適用 gate。

修正未達預期時，保留目前工作樹和 evidence，依上方[回跳條件](#開發-loop-與回跳)在既有授權及安全前提內繼續定位、最小修正與驗證。若下一步需要資料／外部狀態恢復、破壞性操作或新的風險決策，先核相應 recovery procedure、授權及適用 gates；必要條件缺失時只停止依賴部分，保留 blocked、恢復所需 owner／條件及重開方式。不自動 reset／clean／force 或丟棄既有修改。

## 最小回寫與 Exit

產品／業務語義回其 canonical owner；技術契約回系統設計或明確 native owner；工具 binding 回[項目工程入口](../項目工程入口.md)所指唯一 source；本次進度與觀察回既有 tracker／dated record。只有必要 owner 或入口變動時才同步[項目文件來源目錄](../../README.md)或 derived view。Exit 說明改動 scope、實際驗證層、partial／blocked、NOT_RUN、未解風險及後續 owner；需要交付再走[版本交付](版本交付.md)。
