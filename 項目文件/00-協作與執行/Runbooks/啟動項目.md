# Runbook：啟動項目

## Trigger 與完成範圍

用於建立新項目的全局產品骨架，或重新確認會改變產品方向／主要 scope 的重大重定向。單一 feature 深化走[開發與變更](開發與變更.md)，不重開全套 brainstorm。啟動可交付分析、proposal 或已確認的 current skeleton。Ready 必須指明下一個工作範圍，依下方開工準備檢查判定；它不表示整個產品可交付或已被接受。

## 讀者與前提

主要讀者是要求者／產品 decision authority、需求 owner、協作 maintainer 與負責分析的 Agent。開始前讀[工作標準](../規則與標準/工作規則與標準.md)、[項目文件來源目錄](../../README.md)，需要 repo／工具／環境時讀[項目工程入口](../項目工程入口.md)。收集現有 current／draft 文件、原始需求／研究來源、已知限制、現行產品與技術 evidence；不要先覆寫舊內容。

## 按需檢查

- 這是新產品方向、重大重定向，還是可由局部規格承接的深化？
- 誰提出要求，誰有確認範圍的權限？哪些輸入只是觀察／假設／研究？
- 要改善的可觀察結果是甚麼？current 與 intended 有何差異？
- 哪些人是真正 user／actor，哪些人是 stakeholder、buyer、operator 或 approver？
- 哪個未知最可能迫使全局返工或造成資料／權限／相容性風險？
- 近期功能是否已有可判定行為與 acceptance owner？哪些細節可延後到局部深化？

若答案可由現有 owner 和確認事件找到，引用它；只有會改變下一步的缺口才提出決策。

## Brainstorm 與確認

先按已有資料整理問題、角色、主流程、範圍及假設，清楚區分可回查事實與建議。找出最可能迫使全局返工的缺口；需要取捨時，向有權決策者提出具體選項、推薦及代價，只問正式來源無法回答且會改變下一步的問題。已有授權及確認足夠時直接深化，不重問已決事項，也不一次丟出整份模板問卷。

取得確認後，只回寫該次確認涵蓋的 scope／revision；新答案改變重大方向、權限、資料政策或外部承諾時，再回到相應決策點。未確認的部分保留假設／proposal，已授權且無依賴的工作可繼續。這個循環按需要重用；具體產品內容依下面的程序落到各自來源。

## 操作程序與分支

1. **確定範圍**：用[項目文件來源目錄](../../README.md)找現有產品／流程／技術 owner。標記資料的來源、scope、revision、確認狀態與限制；資料來源或可改性有歧義時，按工作標準的[資料來源與表示權威](../規則與標準/工作規則與標準.md#資料來源與表示權威)保留未解部分。既有 current 保持原樣，除非變更本身已獲授權。
2. **整理問題與成果**：描述目標對象、現況、問題、期望結果、non-goals、時間／法規／技術／營運限制和必要 transition。將事實、使用者自述、推論和 unknown 分開。
3. **整理角色與情境**：明確 users、stakeholders 和決策者。以具體情境記錄 actor、context、trigger、問題、目標和期望整體結果；不要把採購／批准角色自動當成 user，也不要把情境當成新模組分類。
4. **建立範圍骨架**：在產品需求 owner 承接全局問題、scope、能力／版本取捨、主要 user groups、品質目標、主要情境、需求來源及確認引用。先辨識全局主流程、模組責任、關鍵狀態與高影響政策，以及主要架構、資料責任、外部依賴和必要 UI／契約方向；業務內容落在 02，技術方向落在 03，少量內容可各自分章合併。近期功能再深化行為、重要分支及 AC，不要求所有遠期功能先有完整規格。只有獨立跨步交接需要時才建立流程文件；重要取捨回決策紀錄。草稿格式按內容選用[產品骨架範本](../../../文件模板/產品骨架範本.md)、[模組與功能規格範本](../../../文件模板/模組與功能規格範本.md)、[業務流程範本](../../../文件模板/業務流程範本.md)或[技術設計與契約範本](../../../文件模板/技術設計與契約範本.md)；產品／業務決策權不隨技術表示轉移。
5. **分開輸入整理與需求採納**：
   - 先在來源對照記錄原始輸入已映射到哪些草稿／正式內容，或哪些仍待釐清、未納入本輪整理；這不表示那些要求已被批准。八項要求可以全部映射，而只有其中六項獲採納。
   - 再核對唯一確認事件的 scope／revision：全部或部分採納時，只將獲確認範圍寫入 current；未確認部分仍是 proposal／pending。Reject／defer 留在原處置來源及其理由，其他位置只引用。
   - 尚無決策權或 evidence 不足：交付有界 proposal／unknown；不要以文件存在、使用者未反對或時間經過推定批准。來源映射欄不另存一個採納狀態。
6. **處理未決與就緒範圍**：全局未知在產品骨架記影響、責任人、下一個查證／決策行動及解除條件；局部未知留局部來源，交接時引用。依[開工準備檢查](#開工準備檢查)給 Ready、Conditional 或 Not ready 的理由；高影響未知有計劃不等於已解決，不得把「約 75%」改成文件數、字數或虛構百分比 gate。
7. **交接**：給近期 slice 一個可觀察結果、規格來源、接受責任、必要依賴及下一步。在既有 task／啟動紀錄只記一次本次判斷：工作範圍與基線、條件依據、可開始的工作、仍阻塞的工作及其未決來源；已由其他紀錄承接就引用，不另造台帳。執行工作改走[開發與變更](開發與變更.md)，沿用已有授權；程序本身不批准設計或擴張實作 scope。

**有界實驗分支：** 若要求者已明確授權隔離 PoC，可在該 scope 採用標明來源的實驗假設，列明不可觸及的資料／帳號／環境及停止條件，再走開發 Runbook。實驗授權可允許實作；它不將假設提升為客戶已接受的 current product contract。不要因客戶接受仍 pending 而停止已獲授權且不依賴該接受的實驗。

## 開工準備檢查

新項目或重大重定向進入開發前，按下列責任核對已有內容與本次工作所依賴的條件。引用已有章節即可，不另填一套同義表；不適用項說明理由，遠期細節可延後。這些條件不代表固定檔案數，也不要求每次局部修改重做啟動。

| 準備責任 | 要能回答的問題與內容落點 |
| --- | --- |
| 全局方向 | 產品問題、scope／non-goals、角色、主要能力與主流程是否已有可依賴內容？由 01 與相關 02 承接。 |
| 業務骨架 | 模組責任、關鍵狀態及高影響政策是否足以約束近期行為？由 02 承接，完整細節不搬入 01。 |
| 技術方向 | 主要架構、資料責任與存取邊界、外部依賴及必要 UI／契約方向是否明確？由 03 引用相應業務要求。 |
| 近期功能 | 本次功能的行為、重要成功／拒絕／失敗分支與可觀察 AC 是否可定位？由功能／流程規格承接。 |
| 未決與風險 | 哪個未知影響方向、安全、資料或相容性？其責任人、處理方式及被阻塞工作能否由原未決來源回查？ |
| 執行與驗證前提 | 下一個工作範圍、已有授權及驗證方法是否明確？命令入口回工程 binding；runner 尚未存在時，列建立入口的下一步，未執行結果保持 NOT_RUN。 |
| 來源與採納 | 本次要求的來源／解讀、採納範圍與確認依據是否可回查？情境是否連到近期能力及其 AC？來源對照不代替批准。 |
| Transition | 初始資料、training、營運交接／支援、cutover／連續性是否適用？適用時由 01／02 定成果、責任與驗收，方法回 03／Runbook。 |

Ready 表示所列下一個工作範圍的必要條件已滿足；Conditional 必須列明可做與仍被阻塞的範圍，並引用解除條件；Not ready 表示所請求的下一步仍有必要前提未滿足，另指出可獨立推進的已授權工作。研究或 PoC 可以是解除未知的方法，不能用其就緒結論替代正式功能的準備或交付判斷。

## 輸出與驗證

輸出是可追溯的產品骨架及必要的情境／模組／設計草稿，配合來源 disposition、確認依據、高影響未知和 Ready／Conditional／Not ready 判斷。只建立內容需要的文件，使用模板時不把模板文字當成產品值。

依開工準備檢查核對各責任的落點，確認 scope 與確認事件一致、user 和 stakeholder 未混淆、輸入映射與採納分開；proposal、拒絕、延後及部分採納均保留原身份。接手者應能從本次紀錄定位可開始的工作、仍被阻塞的部分及所需規格／驗證，不需重新猜測 Ready 的意思。沒有可回查確認者／scope 的內容不得標記為已確認。

## Failure、stop 與 recovery

若方向、權限／資料政策、重大風險接受或外部承諾尚未裁決，停止依賴該決定的 current 化或 downstream work；仍可完成來源盤點和獨立調查。若來源互相矛盾，改走[調查與分析](調查與分析.md)並保留每個 owner 的說法；不能挑較新版本覆蓋舊來源。若既有內容衝突或初始化入口拒絕建立檔案，保留原檔並先確認實際 owner，不能 force、reset 或刪除後重建；任何獲明確授權的破壞性處置仍須按[破壞性操作](../規則與標準/工作規則與標準.md#破壞性操作)完成兩道 gate，執行前重核 exact targets。

若初始化中途失敗，先讀項目工程入口所列 partial receipt／backup／active binding 狀態，核對已建立路徑及草稿 hash；保留原 clone，在新目的地明確採納或由 owner 精準協調。此分支不提供自動刪除、覆寫或強制重試。

## 最小回寫與 Exit

只更新產品骨架及實際承接的來源／流程／技術 owner；必要的確認與決策事件留在唯一來源。把一次啟動結論或 blocker 留在項目指定 tracker／dated record；只更新因來源移轉或新 owner 而失效的 link。Exit 時聲明已確認、proposal、partial、reject/defer、unknown、可開始的工作與被阻塞的工作。單 feature 深化不因此重開啟動流程。
