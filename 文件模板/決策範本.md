## 3. 決定與確認依據

- 決定內容：待填；未決時保留「待填」或「未確認」，不要把建議寫成決定
- 選擇理由及依據：待填
- Decision status：待填
- 確認者及其 authority：未確認
- 唯一確認事件 reference：未確認
- 適用 scope／revision／生效條件：待填
- 若沒有可持久回查的 reference 且確需追溯，最小 receipt：確認者／權限、時間、確認的內容、scope／revision、依據或限制；否則填「N/A（引用已存在事件）」並列出該 reference。

一條確認事實只記一次；本決策可覆蓋其 scope 內多項需求，不要求每條 derived rule 或 AC 重新批准。不同 scope／revision 可有各自事件。本節是由本決策紀錄擁有的唯一 decision status 與 confirmation event；header 及其他文件只引用此 event。只有重要取捨需要 DEC／ADR。一般明確確認應優先引用既有 chat、task、meeting 或 issue；不得在產品骨架來源表、各規格 header 及本紀錄各存一個互不相連的批准狀態。

## 5. 先自答、邊界與最低完成

此節是 review prompt，不是新增必填問卷：只補上文尚未回答且會改變下一步的資訊；已記載的值引用章節，不重複填。簡單決策可短答，無關處標 N/A 及理由。

- 這是會影響未來 scope／架構的取捨，還是一般局部實作細節？待填
- 誰具決定權；scope／baseline 是甚麼？待填
- 候選選項、代價及未知是否可比較？待填
- 哪個事件是唯一確認 reference；若尚未決定，current 是否仍維持未確認？待填
- 哪些 current normative owners 因決定而變更，哪些只需核引用？待填
- 如何處理 supersede、兼容及重議？待填

**邊界：** 決策紀錄擁有取捨理由、決策狀態、影響及取代關係；產品／技術正文仍由相應 current owner 擁有。本紀錄不追蹤工作任務、驗證紀錄或交付紀錄的執行狀態，不為每個小改動強建一份決策文件。

**最低完成條件：** 決策問題、scope、authority、選項／理由、狀態、唯一確認依據（未決時明確為未確認）、受影響 current owners、必要回寫與重議條件均已記錄；未有權限或證據時狀態仍待填／未確認。
