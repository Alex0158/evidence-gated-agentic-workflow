# 工作任務｜{{PROJECT_NAME}}

> 本模板描述一次可追蹤的工作 instance，也可用於先捕捉尚未查清的待處理項。依[任務登記與分流](../項目文件/00-協作與執行/Runbooks/任務登記與分流.md)先作有界查重並核主源；重要發現遇到查重不足／主源不可用時，可在允許位置先保留待查重／待登記紀錄，再對帳。已有 issue/task tracker 可用時引用它，不另做一份同步台帳。

入口：來源與內容 owner 見 [項目文件來源索引](../項目文件/README.md)；任務分類、授權與程序見 [00 工作入口](../項目文件/00-協作與執行/README.md)及[工作標準](../項目文件/00-協作與執行/規則與標準/工作規則與標準.md)。

## 首次最小登記與補齊時點

首次登記只需下列資訊可定位；直接填在下方對應章節或既有 tracker，這張表是欄位提示，不另填第二套值。未知可寫 unknown／待評估／待指派，並留下下一個判斷行動；完整根因、規格或實作計畫不是捕捉前提。

| 首次需可定位的資訊 | 本範本落點 |
| --- | --- |
| 主源或暫存的唯一定位：平台 ID，或可回查的檔案／章節及標題 | 第 0 節；暫存明示待查重／待登記，不當成已入主源；平台未配置 ID 時不臆造一個 |
| 問題／目標、來源／發現時點及已知觀察的證據身份 | 第 0、1 節；事實、來源聲明與假設分清 |
| 已知 scope、功能／業務影響及風險或尚未知處 | 第 1、2 節；完整分析用引用 |
| 暫定分類、處置／tracker 狀態及優先級／待評估理由 | 第 0 節；採項目既有值，不預填已批准或已排程 |
| 下一動作責任，或待指派及由誰確認責任的下一步 | 第 0、3 節；不以填姓名推定已承接 |
| 下一最小行動／Route、所需決策／依賴及本次完成層 | 第 1、3 節；未授權動作保持待決 |

進入下一程序前，按該動作補足必要 scope／baseline、允許動作、正式依據或待調查差異、前提、完成／停止及驗證條件；不要求調查任務先有完整實作規格。關閉時再補實際結果、處置依據、回寫與 handoff／重開條件。相同內容只有一個值來源，其他章節引用；本模板不強制每項填滿才准登記。

Issue 可擁有問題、優先級及風險，implementation task 可擁有一次工作進度；兩者若不同，分別連結，不把其中一個狀態複製為另一個。Task Done 不自動 close Issue、令驗證紀錄通過、令交付紀錄部署或代表 user acceptance。

若工作或 claim 標為 BLOCKED，依[工作標準的結果／狀態規則](../項目文件/00-協作與執行/規則與標準/工作規則與標準.md#結果與狀態)分開記錄 blocker、run result、cause 與 owner；本 task 只擁有工作／依賴狀態，不由 BLOCKED 推定根因、PASS 或 non-defect。

## 1. 目標、current 與預期結果

- 要解決的問題／本次目標：待填
- Current／observed 狀態及證據身份：待填（已觀察／來源聲明／推論／假設）
- Intended 狀態／成功條件：待填；引用 normative owner，不在 task 重寫產品規則
- Scope 內的 repo、文件、功能、環境或 artifact：待填
- 明確 scope 外項目：待填；無則填「無」
- 哪些動作已授權；哪些需要別的決定／確認：待填
- 本次工作完成層：待填（調查／文件／source／驗證／交付／接受；可部分交接）
- 後續工作處置／關聯主源：待填（更新既有項／新增待處理／本次已處理／無後續／待登記等文字描述）；記理由及實際 reference，不將描述當成全局 status enum

- 原問題與適用契約／失敗 evidence；目前原因假設、支持／反證及信心／未決分開。反證須說明推翻甚麼；只推翻原因假設不代表原問題已被否定，非缺陷判斷須有該 scope 的問題／契約證據。
- 下一個最小查證／修正及既有授權 scope；交接時連原失敗／基線、修正範圍與修後對應 check。實際觀察只留 VR／native run，根因判斷與行為回歸的 claim 分清。

## 4. 驗證、回寫與 closure

- 實際驗證使用的驗證紀錄 reference：NOT_RUN；run 尚未執行時保留此值與阻塞原因
- 實際交付使用的交付紀錄 reference：NOT_RUN；沒有交付 scope 時填「N/A」及理由
- 規範正文回寫／只核引用／派生索引更新：待填；未變更時寫原因
- 本次剩餘未完成、風險與明確 handoff：待填
- Task closure 條件及處置依據：待填；達成本次目標才完成該 instance。調查目標完成且成果可回查時，可完成調查 instance，後續尚未承接仍記待交接；目標本為完成交接時，另需可回查承接結果。未完成的實作只記待續／轉交，不以 handoff 文字標 Done
- 延後／拒絕／duplicate／風險接受（適用時）：引用有權處置、scope、理由、責任及重議條件；未裁決保持建議／待決
- Reopen／追加工作條件：待填

## 5. 邊界與最低完成

**邊界：** Task 擁有本次工作計劃與進度，不擁有長期產品規則、決策批准、run 證據或交付結果。每個 instance／狀態維度一個 primary tracker；不同維度可有不同 records。由新證據發現的規則改動須回 current normative owner，不能只寫在 task。

**分階段最低條件：** 首次捕捉依「首次最小登記」即可；下一步執行前補該動作需要的授權、scope、依據、影響、前提及完成／停止條件；closure 另核實際結果／處置、必要驗證／交付 reference 或 NOT_RUN／N/A 理由、回寫、handoff 及重開條件。Unknown／pending 保留明確身份與後續判斷，不用一次填滿所有章節，也不把登記完成當成工作或原 Issue 已完成。
